# claude
Claude Code integration for yena.

It is a yena plugin (`runtime: "node"`, `entry: src/index.ts`, version 0.8.0): the host loads it at startup and adds the `claude` command. It requires core 0.4.0+ for the console tools and core 0.5.0+ for the live Bash panel (`MountOptions.activity`, kit `OutputTail`) and core 0.5.1+ for Markdown tables (kit `styledCells`; a named import, so the module fails to load on an older core) and core 0.6.0+ for the chat spinners (kit `SPINNERS.sparkle`, `SPINNERS.blink`; the chat view fails to render on an older core); older cores work without them (core is declared in `yena.json`, without a version): text helpers and UI pieces come from core's public kit, imported only through `src/kit.ts` and `src/ui/kit.ts`; the md hub's path and folders come from md's public entry through `src/deps/md.ts`; `ping` and `ask` never load React, Ink or the kit UI. `claude ask` and `claude chat` run the Claude Agent SDK in a read-only mode.

## Commands
- `claude ping` — prints `pong`; confirms the module is loaded.
- `claude ask [--new] <text>` — asks Claude, continuing the last session. `--new` starts a fresh session. Use `--` before text that starts with `--`. Text starting with `/` is rejected. Only one ask runs at a time; an ask is cancelled after 5 minutes. Output ends with a footer:
  ```
  Asking Claude…
  <answer>
  [session d503c507 · model claude-haiku-5-5 · subscription token]
  ```
- `chat [model]` — top-level command: opens a new chat (fresh session) with `model` or, without it, the chat model from the settings. It has `autostart: true`, so core opens it at startup, and it contributes the `Claude` settings tab, stored in `state.json` (unset keeps the Claude Code default): `Permission mode` (`chatPermissionMode`: Default, Accept edits, Auto), `Chat model` (`chatModel`: Default, Fable 5.1, Opus, Sonnet, Haiku), `Effort` (`chatEffort`: low…max, SDK `effort`), `Thinking` (`chatThinking`: Adaptive or Off, SDK `thinking: {type: 'disabled'}`), `Fast mode` (`chatFastMode`, settings flag `fastMode`), `Output style` (`chatOutputStyle`: Explanatory or Learning, settings flag `outputStyle`), `MCP servers` (`chatMcp`: On by default, servers from the Claude Code config; Off keeps `strictMcpConfig`), `Settings hooks` (`chatHooks`: Off by default; On sets `disableAllHooks: false`; yena's policy hook runs either way), `Keep working after exit` (`chatKeepRunning`: Off by default, see "Background chat"), `Input mode` (`chatInputMode`: Normal or Vim). MCP and hooks apply to new chats. All of them apply to the open chat at once (`Query.setModel`, `setMaxThinkingTokens`, `applyFlagSettings` for effort, fast mode and output style; a respawned query gets them in its options) and to new chats. Code: `src/chat-prefs.ts`. A model argument must match `[A-Za-z0-9][A-Za-z0-9._[\]-]*` (at most 100 chars) and is used for that chat only.
- `claude chat [--new]` — opens an interactive streaming chat (see below). Continues the last session; `--new` starts a fresh one. Uses the chat model from the settings.
- `claude new [model]` — opens a new chat, like `chat [model]`.
- `claude resume [session]` — continues an earlier chat of this project. Without an argument a list opens in the console (newest first: Claude Code's title or the first prompt, age, number of prompts; ↑↓, Enter resumes, Esc closes); with an argument the session whose id starts with it is resumed. The resumed chat shows its last 40 prompts and answers (text only, tool calls left out), read from `config/projects/<project>/<session>.jsonl` (`src/chat/history.ts`).
- `claude rewind` — a list of your messages in this chat (newest first); picking one restores the files Claude changed since then (Claude Code file checkpoints, `enableFileCheckpointing`, `Query.rewindFiles`) and reopens the chat on a branch from just before it (`forkSession` + `resumeSessionAt`), with that message back in the input. Rewinding to the first message opens a fresh chat.
- `claude fork` — continues the current (or last) chat on a new branch; the original stays as it was.
- `claude rename <name>` — names the chat (a `custom-title` entry in the transcript, as Claude Code's /rename writes); the bar shows it.
- `claude export [file]` — writes the chat's prompts and answers as Markdown, by default to `<dataDir>/exports/<date>-<session8>.md`; a given path must be inside the project or the data directory and must not exist yet.
- `claude copy [N]` — puts Claude's last (or Nth last) answer on the terminal clipboard (OSC 52 through core's `ctx.copyToClipboard`; at most 50 000 characters; the terminal must allow OSC 52).
- `claude memory [file]` — opens `CLAUDE.md` (or another md file in `md/`) in `$VISUAL`/`$EDITOR`/`vi` through the terminal handoff.
- `claude tasks` — the chat's tasks (background Bash, subagents) with status and age; picking a running one stops it (`Query.stopTask`).
- `claude mcp [reconnect <server>]` — status of the chat's MCP servers (after its first message), or reconnects one.
- A new chat starts on a clean screen (core clears its transcript when a chat view mounts).
- `claude code [args…]` — runs `<module>/bin/claude` (Claude Code) in your terminal via `ctx.suspend` (no shell; agent policy `deny`). Errors: no terminal hand-over (`"claude code" needs an interface that can hand over the terminal`), wrapper missing (`Run modules/claude/bin/install.`), non-zero exit (`Claude Code exited with status N`; exit 1 from the terminal, in the UI it waits for Enter first). Logs only the argument count and status. Limits: core re-splits the line on whitespace (`./yena claude code -p "a b"` becomes `-p a b`), 4096 chars, no control characters; workarounds: pipe the prompt, or run `modules/claude/bin/claude` inside `./yena sh`. The first run may self-update (~12 s).
- `claude sessions` — shows the running chat or ask, in any yena or in the background (kind, where, session, since when). Safe for the assistant.
- `claude stop [session]` — stops the running chat or ask. For a background chat it first asks the runner over its control socket, then sends SIGTERM and SIGKILL, but only to a process verified as our runner (argv ends with `src/runner/main.ts`; pid and process start time match the lock). A chat in another yena cannot be stopped from here (close that yena). Needs confirmation when the assistant calls it.
- `claude session` — prints `Session`, `Model`, `Chat model`, `Claude Code runtime`, `Agent SDK` and `Binary in use` (`runtime` or `bundled`).
- Several Claude accounts, in priority order (`src/accounts.ts`): a new turn uses the first account that has not hit its limit. When the turn hits a usage limit (or a billing error), that account is set aside until its reset time (from Claude Code's limit report; 5 h without one, 24 h after a billing error), Claude Code restarts with the next account **in the same session**, and yena sends it `Continue from where you stopped; the previous attempt was cut off by a usage limit.` so the turn goes on. The chat prints `Account "work" reached its usage limit; continuing with "spare".`; `claude ask` does the same and prints the same line. With no account left, the turn ends with the usual `Usage limit reached…` message. Once the limit of a higher account has passed, the next start of Claude Code (a chat closes it after 15 s idle) goes back to it. At most 8 switches per turn.
  - Accounts: `env-key` / `env-token` (`ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` from the environment; part of the order, not removable), API keys and subscription tokens stored by yena, and Claude Code browser logins. Default priority (before any `order`): environment, logins, then stored keys and tokens in the order they were added.
  - Logins: Claude Code keeps one login in its config dir, so each login account has a slot `<dataDir>/accounts/<name>/login.json` (0600, dir 0700) with `config/.credentials.json` and the `oauthAccount` / `primaryApiKey` fields of `config/.claude.json`. Before Claude Code starts with a login account (only while the session lock is held: at a chat turn's start, an ask, an account switch), the login now in the config dir is saved back into its slot (Claude Code refreshes and rotates its tokens) and the chosen one is put in; the rest of `.claude.json` (settings, MCP servers, projects) stays, and Claude Code's per-organisation caches `policy-limits.json*` and `remote-settings.json*` are deleted so they are fetched again. A login made directly in Claude Code (e.g. with `./yena claude code`) is noticed by its account id and taken as a new account instead of being saved over another one.
  - Store: `<dataDir>/accounts.json` (0600): accounts, order, limits (`until` epoch seconds, `usage-limit` or `billing`) and which login is in the config dir. An old `credentials.json` becomes account `stored` and is deleted; a login already in the config dir becomes an account named by its email. Names: up to 64 of letters, digits, `. _ @ + -`.
- `claude start <message…>` — opens a new chat and sends it the message (the open chat is saved and can be resumed). Policy `confirm`, so an assistant (with the user's approval) and the scheduler (`scheduler add … cmd claude start …`) can use it; it returns once the chat is up. Run by them, it shows the chat in the main area through the context of the chat's own command (`chat`, autostart); refused while a chat is answering.
- `claude send <message…>` — sends the message to the chat that is open, as if typed there (queued while it answers, refused past the queue limit). With no chat open it starts one, as `claude start`. Policy `confirm`. The task form's "Save and discuss" uses it.
- `claude auth accounts` (also `auth list`) — the accounts in priority order: `▸` marks the one used next, each line has the kind (login with subscription/Console and email, key, token, environment variable) and, while set aside, `limit reached, back at <time>` or `billing failed, …`. Names and emails are shown on screen only, never logged.
- `claude auth order <account> [<account>…]` — puts these first, in this order; the others keep their order after them. `claude auth use <account>` — moves one to the top and forgets its limit. `claude auth remove <account>` — removes a stored account; removing the login that is in the config dir also takes it out of there (Claude Code is signed out of it).
- `claude auth status` — the active credential (for example `Active credential: account "work": subscription token (stored by yena)`), the account list when there is more than one, file-mode warnings and the one-time subscription notice.
- `claude auth key --from-file <path> [--name <account>]` — stores an API key from a file as an account (default name `key`, then `key-2`…; the same name replaces its key; the same key twice is refused). The source file is left untouched; delete it yourself. Notes when the new account is not the one used next.
- `claude auth logout` — takes no arguments. Removes every stored account (keys, tokens, login slots, `accounts.json`) and the login in the config dir; when Claude Code still reports a login it also runs the CLI's `auth logout` non-interactively (30 s, output discarded) and warns if a login remains. Environment variables are untouched. `auth remove <account>` removes one.
- `claude auth login [--name <account>] [--console|--claudeai] [--sso] [--email <address>]` — hands the terminal over (core `ctx.suspend`) and runs Claude Code's own browser login with the module's config dir and without credentials from the environment. The login there before is saved into its account first; afterwards the new login becomes an account (named by `--name`, else its email; signing in again to the same Claude account updates it). Refused while a chat is answering. Argument errors show even without a UI.
- `claude auth login --token [--name <account>]` — runs `setup-token`, asks for the printed token with hidden input and stores it as an account (default name `token`); the token never goes through arguments, history or logs. Use it when the long login URL breaks when copied out of the terminal; several tokens of different subscriptions can be added this way.

- `claude <command> [args…]` — any other name is a Claude Code command (built-in such as `compact` or `context`, a custom command from `config/commands`, a skill): it is sent to the open chat as `/<command> args` and runs there, its output appears in the chat. Without an open chat it fails with `No chat is open…`; while Claude is answering it is refused; once the session has reported its command list, names outside it are refused. Hints after `claude ` list the session's commands (with descriptions and argument hints from `supportedCommands()`), or, before the first message, the custom commands and skills found in `config/`.

Without a subcommand the command fails with `Usage: claude <ping|ask|chat|new|resume|rewind|fork|rename|export|copy|memory|tasks|mcp|session|sessions|stop|auth|<Claude Code command>>`.

`<dataDir>` is `<YENA_DATA>/claude` (`/data/claude` in the container). It holds `md/`, `config/` (including Claude Code's own login files `config/.credentials.json` and `config/.claude.json`, plus `config/backups/`), `state.json`, `accounts.json` and `accounts/` (see the accounts above). `md/` is a symlink to the shared hub of the `md` module, `<YENA_DATA>/md` (a dependency in `yena.json`), so instructions and Claude Code config folders are shared with other agents. The hub holds `agents/`, `skills/`, `commands/` and `output-styles/`; `config/<folder>` is a symlink to `../md/<folder>` so Claude Code finds them (`MD_LINKED_DIRS`; settings and hooks stay in `config/`, since they can run code and change permissions). The links are created when missing at the start of a chat or ask (and by `bin/claude`): an old real `md/` moves into the hub while the hub is blank, a real `config/<folder>` moves into the hub while the hub's folder is empty; otherwise they are left alone (`ensureMdLinks` in `src/config.ts`). Claude is pointed at the hub's own path (system prompt hint, `additionalDirectories`).

## Chat
`chat` and `claude chat [--new]` show the chat as core's main view (needs a core that provides `ctx.mount`; otherwise it fails with `"claude chat" needs an interface that can show views`). Opening a chat closes the open one first; a chat cannot run together with an ask (`A chat is already open`, `An ask is already running`). Unknown arguments give `Usage: claude chat [--new]` / `Usage: chat [model]`.

Next to core's console (`control.host` present) the chat reads keys only while focused, lays out in the width the host gives, ignores the console toggle (`§` or Ctrl+T, via `host.isHostKey(input, key)`), ignores core's host keys (Shift+←/→ move the focus, Ctrl+T toggles the console); Tab with no `@`/`/` suggestion list open opens or closes the console (`host.togglePanel()`), with a list it completes, Shift+Tab cycles the mode, moves the input to the console with → on an empty draft, and Esc never leaves it (only Ctrl+C does) and never opens the console: Esc clears the draft or interrupts, and does nothing while an interrupt is pending.

Keys:
- Enter sends. Alt+Enter or Shift+Enter inserts a newline; a bracketed paste is inserted sanitized and never submitted. The input soft-wraps by words over up to 10 rows (half the free space at most; widths by grapheme, wide characters count as two), so all of a typed line stays visible; a longer text keeps the cursor's rows in view. In permission prompts and questions the header, the options and the key hint wrap instead of being cut, and the typed `Your answer:` / `Reason:` wraps under its label; the framed body gives up the rows they take. Input is limited to 32000 characters (`Input truncated to 32000 characters`).
- Esc while an answer runs interrupts it; the next message continues the same conversation. Esc while idle clears the draft, or leaves the chat when the draft is empty. Ctrl+C interrupts a running answer, or leaves the chat when idle.
- Enter while an answer runs is refused (`Wait for the answer or press Esc to interrupt`) and the draft is kept; there is no message queue.
- `:q` (or `:q!`) as the whole message exits yena (through `host.quit()`; without a host it leaves the chat); it is never sent.
- Slash lines (needs core 0.6.0+ `ViewHost.runLine`/`listCommands`, feature-detected in `src/ui/view-commands.ts`; on an older core every line goes to Claude): a one-line `/<command> [args]` whose first word is a yena console command runs in the console (which opens beside the chat, the input stays in the chat; the chat prints a dim `/<line> → console`), e.g. `/project list`, `/settings`, `/chat`. `//text` sends `/text` to Claude. Any other line, a `/word` that is not a console command included, is sent to Claude as written (`client_composed`, so Claude Code does not run it as a command; such a turn also skips Claude Code's per-turn attachments). Typing `/` lists the matching console commands with their descriptions above the input (`src/ui/slash.ts` `slashHints`; prefix matches first, at most 6): ↑/↓ choose, Tab takes the highlighted one, Enter takes it too unless the typed name is complete or the line ends with a space (then Enter runs it), Esc hides the list. After a command and a space the list goes on with its subcommands (aliases count too), e.g. `/claude ` lists the chat commands and the Claude Code commands, `/project ` its subcommands; nothing is hinted for arguments. Subcommands need core 0.7.0+ (`listCommands()` with `subcommands`); the list is read at most once a second while typing. Claude Code commands run as `/claude <command>` (forwarded to the open chat as `/<command>`).

Permission modes: the `Permission mode` setting (`chatPermissionMode` in `state.json`) is the mode new chats start in and switches the open chat at once. Shift+Tab still cycles default → accept-edits → plan → auto for the open chat only (switching to accept-edits or auto asks for confirmation with Enter).
- `plan`: SDK `permissionMode: 'plan'`; Claude researches and proposes a plan without changing anything. When it calls `ExitPlanMode` the prompt asks to start (Yes: default mode; "Yes, and accept edits": accept-edits; No with a reason: Claude keeps planning). Plan needs no confirmation to enter. Claude Code writes the plan to `config/plans/`, the one part of the config dir Claude may write: the chat's settings deny the rest by listing its parts (`CONFIG_EDIT_DENY` in `src/policy.ts`), and the policy hook refuses any other write into the config dir, symlinks resolved.
- Writes: the md hub (`<YENA_DATA>/md`, at its own path) is Claude's own: Edit/Write there never ask, in any mode (class `free`; the chat settings allow `Edit(<hub>/**)`, so auto mode's classifier skips it too; secret-looking names stay denied). The hub's root `CLAUDE.md` and `SOUL.md` are not free: every session and agent loads them, so a change there would be a persistent prompt injection. Edit/Write on them always asks (class `prompt-only`, `ask` rules in the chat settings, and the policy hook answers `ask`, which forces the prompt in auto mode too). Another exception: in the hub's `agents/`, `skills/`, `commands/`, `output-styles/` and in any `.claude/` folder, the policy hook refuses an Edit/Write that adds or changes the frontmatter keys `allowed-tools`, `hooks`, `permissionMode` or `mcpServers` (near spellings included; removing them is fine), because they let later tool calls skip the prompts (`src/chat/definition-guard.ts`); the user makes such changes by hand. Bash writes are not checked. The data dir `<YENA_DATA>/claude` is closed for writes by the given and the resolved path (class `deny-locked`), including the `md` link and the `config/<folder>` links into the hub; the one exception is `config/plans/`, where plan mode writes its plan. The chat settings carry no deny rule for the `md` link or the linked `config/<folder>`s: Claude Code resolves symlinks in rule paths, so such a rule would deny the hub itself (the policy hook refuses those paths instead). When yena runs outside the container (data under `./.yena`) the `Edit(./.yena/**)` deny rule also closes the hub.
- `default`: every Edit/Write and Bash call asks.
- `accept-edits`: Edit/Write inside the project are accepted without asking (the bridge decides; the SDK stays in `default`).
- `auto`: the SDK `permissionMode: 'auto'` — Claude Code's model classifier approves or denies each tool call and only asks (through the usual prompt) when it cannot decide. A running query is switched with `Query.setPermissionMode`; a new one gets it in its options. If the SDK rejects it (account, model or version without auto mode), the chat falls back to `default` and prints `Auto mode is unavailable: <reason>`.
- The hard path policy holds in every mode: a `PreToolUse` hook (`src/chat/policy-hook.ts`, passed as the SDK `hooks` option, which `disableAllHooks` does not cover) denies reads outside the roots, Edit/Write outside the project or into guarded/secret paths, and background Bash, even when the classifier approved the call. Settings deny rules still apply too. What auto mode does not limit: Bash commands inside the container that the classifier approves.

Display, modelled on Claude Code's terminal UI:
- Scrollback: one empty line before every block (a permission audit line stays attached to the block after it). Your message is a grey `> …` block; Claude's answer starts with `●` and its lines hang two cells under it (wrapped by yena at the chat width, and laid out again through `PrintOptions.render` whenever the transcript width changes, e.g. on resize or when the console panel opens or closes, so answers printed beside the console fill the chat once it closes; a resumed chat's earlier answers too); a tool block is `● Name(args)` (green dot, red on error; name bold, arguments plain; yena's console tools read `Yena(<command line>)` and `Yena(list commands)`) with the result under `  ⎿  `: Edit `Updated <path> with N additions and M removals`, Write `Wrote N lines to <path>`, Read `Read N lines`, Glob `Found N files`, others the first 3 lines plus `… +N lines (ctrl+o to expand)`; tool arguments, paths, result lines and permission audit lines are never cut with `…`, they wrap at the chat width; thinking is a dim `✻ Thinking…` block cut to 6 lines.
- Live area, top to bottom: the streaming tail, running tools (`● Name(args) Ns`, the dot blinks), the working line (`✶ Working… (12s · esc to interrupt)`, or `Thinking… (1m 12s · ↓ 3.4k tokens · …)` from Claude Code's thinking estimate, `Writing Edit…` while a tool call's input streams, `Compacting…`, `Retrying …`, `Interrupting…`; after 60 s without any event it adds `no response for …`; spinner `SPINNERS.sparkle`, Claude Code's orange), the open checklist under it (`⎿  ☒ done` struck through, `☐` open, the current item bold), queued messages, notices, the input between two rules, and the mode hint under it (`⏵⏵ accept edits on (shift+tab to cycle)`, `⏸ plan mode on …`, `⏵⏵ auto mode on …`; nothing in default mode). On short terminals the rules and the hint are dropped first. Mouse clicks on the input account for the rows under it (`src/ui/ChatView.tsx` `belowInput`).
- A completed answer or tool block is printed once into the scrollback. Next to core (`host.setTitle` present) a bar above the chat shows the chat's name on the left and the status on the right: `5646e143 · claude-haiku-5-5 · 5h limit 85%, resets 15:00 · idle · 1 in background` (session prefix, model, usage limit when one applies, phase or `awaiting approval`, running subagents and background work); the mode is shown under the input, not in the bar; without a host the same status is the last line of the chat. No cost is shown. The name is `New chat`, then the first message (first line, at most 60 characters), then the title Claude Code generates (`ai-title`, or a `/rename` `custom-title`) read from the session transcript `config/projects/<project>/<session>.jsonl` after each turn and again 3 s and 10 s later; a resumed chat reads it at once (`src/chat/title.ts`). Leaving prints `[chat closed · session <id8> · model <model>]`.
- A new chat (not a resumed or reattached one) opens with a dim box at the top of the transcript (`src/ui/banner.ts`), at most 100 columns wide. It shows the widest logo that fits the chat: a shadowed paw print beside the `YENA` wordmark (from 60 columns), the paw alone (from 23), or the plain word `YENA` (from 8; narrower, no box). Next to it go `yena <version> · model <model or default>` and the installed modules with versions: on the right when all of it fits there and is no taller than the logo, otherwise below. When narrow the head splits into two lines, the module list moves under its `modules` label, and is left out when even that does not fit. It is printed with `PrintOptions.render`, so core's transcript lays it out again whenever the chat width changes (an older core keeps the box of the opening width). Versions come from the host's `PluginHost.build`; without it the version reads `unknown` and there is no module list.

Behaviour and limits:
- One streaming query per chat; a turn ends at the SDK `result`. After an interrupt the same query is reused; if no result arrives within 8 s it is recycled and the next message respawns it with `resume`.
- Subagents: the chat tools are Read, Glob, Grep, Bash, Edit, Write, AskUserQuestion, `Agent`, `SendMessage`, `Skill`, `TodoWrite`, `WebSearch` and `WebFetch`, so agents from `config/agents` (and `claude pipeline …`) run. They run in the foreground and in place: `run_in_background` and `isolation` (worktree, remote) are denied (`src/chat/agent-policy.ts`, in the bridge and the policy hook). Starting an agent does not ask; each tool call it makes goes through the same prompts, mode and path policy. Subagent messages are not shown; the running `Agent(<type>: <description>)` line shows its latest tool call (`→ Edit(/app/src/x.ts)`). `claude ask` still has no agents.
- `Skill`, `TodoWrite` and `WebSearch` run without asking. `WebFetch` asks for every host until the user picks "Yes, always for <host>" (the prompt shows the URL and warns that it leaves the container); the policy hook makes auto mode ask for a new host too, since a URL can carry data out. Allowed hosts are kept like Bash "always" rules (`web:<host>`) and listed in the settings tab "Permissions", where they can be removed. The open TodoWrite checklist (☐ pending, ☐ bold in progress, ☒ done; at most 8 rows) shows under the working line until everything on it is done; its tool block is one line (`checklist: 2/5 done`).
- Input: ↑/↓ walk through the messages sent in this run of yena (the draft comes back after the newest); Shift+↑/↓ still scroll. Enter while Claude answers queues the message (`↳ queued: …`, at most 20); the queue is sent as one message when the turn ends, and goes back into the draft if the turn was interrupted or failed with a limit or context error.
- Editing: Ctrl+A/E (line start/end), Ctrl+U/K (kill to start/end), Ctrl+W and Alt+Backspace (kill word back), Alt+D (kill word forward), Ctrl+Y (put the last kill back), Alt+B/F and Ctrl/Alt+←/→ (word moves), Ctrl+_ or Ctrl+/ (undo). Ctrl+R searches the sent messages (type to narrow, Ctrl+R again for older, Enter takes the match into the input, Esc cancels). Ctrl+G opens the draft in the external editor. `@` lists project files (skipping node_modules, .git, build output, .yena and secret-looking names; read on the first `@`), ↑↓ choose, Tab or Enter completes; Claude Code reads mentioned files, images included.
- Vim mode (`Input mode` setting): Esc enters NORMAL (`-- NORMAL --` under the input), `i a I A o O s S C` and `:` go back to INSERT; `h l 0 ^ $ w e b` move, `x X D dd dw de db d$ cc cw yy p u` edit, `j k` walk the history, Enter sends. Esc in NORMAL, or while Claude answers, does what Esc does in the chat.
- Ctrl+O opens the whole transcript of the chat (prompts, answers, thinking, every tool call with its input and up to 400 lines of its result), read from the session file and wrapped once per width (`viewerRowsOf`), so scrolling stays smooth on long chats; ↑↓ or j k scroll, space/b by a page, g/G to the ends, Esc, q or Ctrl+O close.
- Mouse (needs a core whose `ViewHost` provides `subscribeMouse`; feature-detected, older cores lack it, `src/ui/view-mouse.ts`): a left click in the input moves the cursor, only while it is editable (not during permission or question prompts, the Ctrl+O viewer, Ctrl+R search, a pending mode switch or the Waiting row; in Vim NORMAL it lands on a character). The wheel scrolls the Ctrl+O viewer by 1 line while it is open; otherwise core scrolls the transcript. A click can land on the wrong row if a key that changes the input's line count has not been rendered yet.
- Live Bash output (needs core 0.5.0+): while a foreground Bash call runs for 500 ms or more and the chat has focus, the console panel opens (without taking focus) and shows `$ <command> · Ns` plus the tail of the command's output as it is written (polled every 200 ms); it closes when the call ends and core's 3 s grace then applies. Only one panel attempt is made per Bash call, and only when the chat has focus and the panel is free. The SDK sends no start or progress events for a foreground Bash call, so the chat watches Claude Code's own output file (`<tmp>/claude-<uid>/<project>/<session>/tasks/<task>.output`, an undocumented layout) and binds it to a call only when exactly one candidate matches. For that, chats start Claude Code with `CLAUDE_CODE_TMPDIR=/tmp/yena-claude-<uid>` (created 0700, must be owned by you and closed to others, else live output is off and `shell tmp unavailable` is logged). This also moves Claude Code's other temp files, such as background task output, there; `ask` and `bin/claude` are unchanged. Output lines are scrubbed like all other text (at most 200 lines / 32 KiB kept, lines cut at 1024 characters, the last line shown once its newline arrives). Not shown: parallel Bash calls (ambiguous), background Bash, more than 4 simultaneous calls, subagent Bash.
- Ctrl+B moves the running Bash commands and subagents to the background (`Query.backgroundTasks`); the bar counts running subagents (`2 agents`, foreground or not) and background work (`1 in background`), and a settled background task prints `⚙ Background task completed: …`. When a background task ends, Claude Code starts a turn by itself to read its notification; the chat shows it as work like any other turn (`session_state_changed`, enabled with `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS`), so the idle close never ends it midway, and a detached runner waits for it (`TASK_SETTLE_MS`).
- `./yena kill` report: a chat engine (in yena or in a runner) keeps one line about its chat in `$YENA_STATUS_DIR/<pid>` (the yena script sets it): `chat <id8>: idle`, `chat <id8>: working` or `chat <id8>: working, N subagents` (running tasks of type `local_agent`; `new` before the session has an id). It is rewritten on every state, session and task event when the line changes (0600 in a 0700 folder, written to a temp file and renamed) and removed when the chat closes; without the variable nothing is written (`src/chat/process-status.ts`). `./yena kill` prints these lines for the processes it stops.
- Display: answers are rendered as Markdown (headings, bold, italic, code spans, links, lists, task lists, quotes, rules) and fenced code is framed and highlighted (keywords, strings, numbers, comments; `src/ui/markdown.ts`); in the chat the header of a non-empty code block reads `╭─ <lang> · copy`, and a click on that row copies the code as written (scrubbed, without the frame; needs a core with print actions), always after scrubbing, so only constant SGR codes are added. Tables (GFM pipe tables, `src/ui/markdown-table.ts`) are laid out when a finished block is printed, to the chat width minus 1 (100 when the width is unknown): a dim rounded box with a bold header row; cells wrap (columns keep at least 3 cells), and when the table is too narrow for that it falls back to one `Header: value` record per row. Pipes inside code spans do not split cells; tables with more than 64 columns stay plain text. The live streaming tail is rendered the same way while it streams (`liveTail` in `src/ui/present.ts`, wrapped to the chat width minus 1, without the `· copy` labels; tables appear once their separator row arrives, and an unclosed code fence is drawn closed); when the tail is longer than its 16,000-character window, a code fence opened before the window still frames the code in it. Printed answers (tables and code block `copy` rows included) are laid out again at each transcript width; an older core, which ignores a `render` that returns text and actions, keeps the layout of the printing width. Limitations: tables inside lists or blockquotes are not recognised, `<br>` is not interpreted, a link in a header cell resets bold early, and CJK or emoji at a column width of 1-2 cells may exceed it by one cell. Finished thinking blocks print dim before the answer (`✻ Thinking`, first 6 lines) when the API returns their text.
- The turn timeout counts silence: 5 minutes without any SDK message (subagent messages included) ends the turn (`Request timed out: no activity for 300 seconds`). At most 20 turns per user message (reaching it ends the turn with an error and the next message resumes).
- The session id is saved after each successful turn and also after a failed one (limit, context, timeout, cancel) once the session has started, so `claude chat` and `claude ask` continue the same session. The failed message is not restored to the draft because it is already part of the session.
- Limits and context (`src/chat/limits.ts`, no imports so `ask` stays free of react/ink): a usage limit prints `Usage limit reached (5-hour limit), resets at 14:30 UTC (in 1h 20m). The chat is saved; send a message after the reset to continue.` (reset time in the container's zone, UTC unless `TZ` is set, plus a relative `in Xh Ym`; without a reset time the CLI's own text is shown, capped at 200 characters). A temporary 429 prints `Rate limited by the API. Wait a moment, then send again`; `billing_error` prints `The account cannot be billed (billing_error). Check the plan or credits…`. Context overflow (`prompt_too_long`, `blocking_limit`, `rapid_refill_breaker`) prints `The conversation no longer fits in the model's context. Run "claude compact" in the console to summarise it and continue, or "chat" to start a new chat`; `ask` suggests `claude chat` then `claude compact`, or `claude ask --new <text>`. After a limit or context failure the chat stays open: the next send or `claude compact` reaches the same session, and if the stream ended the next send resumes with the saved id. Messages queued when a turn fails (limit, context, interrupt) go back into the draft. Claude Code itself auto-compacts and retries 429/529; this module only adds guidance. `ask` uses the same texts (without chat wording), redacted.
- Early warning: with a subscription (OAuth) credential the CLI sends `rate_limit_event`; when its status is `allowed_warning` or `rejected` the status/title bar gets an indicator such as `5h limit 91%, resets 14:30` or `weekly limit reached, resets Oct 24, 09:00`, which disappears at the reset time. API keys produce no such events. Logs record only `failure: <kind>`, never the CLI text.
- All text shown (model output, tool arguments and results, errors, your own input) is stripped of terminal escapes and bidi/control characters first, then redacted: the Claude credentials, the account module's secret values (read when the chat or ask starts) and common secret shapes (`sk-ant-…`, `sk-…`, GitHub tokens, AWS `AKIA…`, PEM private keys). `ask` output gets the same treatment. This is display hygiene only: what Claude itself reads from a tool is not masked by yena.
- The live area is kept shorter than the terminal (rows-3, rows-1 under 12 rows); on tiny terminals the streaming tail can shrink to nothing and several tools show as `N tools running`.
- Same read-only policy as `ask` (Glob/Grep/Read). Permission prompts, Edit/Write and a diff view are a later phase.

Residual risks:
- Output escaping relies on core's kit sanitizer (`sanitizeBlock`, then this module's redaction), because Ink passes OSC/SGR/bidi sequences through.
- A view that ignores Ctrl+C cannot be interrupted; the chat handles it.
- If yena is killed by SIGTERM/SIGKILL, the `claude` child lingers until its stdin closes (a few seconds; a turn in progress may keep running until then). Closing the chat on unmount is a mitigation, not a guarantee.
- Sub-agent messages are not shown.
- Live Bash output depends on Claude Code's undocumented tasks directory layout: a CLI update can silently disable it (Bash itself is unaffected). Another process running as your uid could plant a file during the short window before a call is bound; the effect is limited to the panel text, which is scrubbed. The uid check and the panel's mouse/TTY behaviour are verified only with tests and fake streams (as root).
- Limit handling rests on reading the Claude Code 2.1.302 binary, not on a recorded session (no fixture): that a `rejected` event may precede the 429 and that `utilization` is a fraction. A usage limit is told from a temporary 429 only by a rejected event or the text `hit your limit|usage limit`, so changed CLI wording degrades to the rate-limit message.
- The container timezone is UTC, so reset times read in UTC unless `TZ` is set (forwarding `TZ` in `compose.yaml` and `tzdata` in the image is a host follow-up, not done).
- A new chat view shows the early warning only after its first `rate_limit_event` (the info is not shared between views).
- Background chat: the client approves a console command run by its bridge-ask id, not by its line (a compromised same-uid runner could ask for one line and run another); the runner trusts anything that can open its 0600 socket in the 0700 directory (no peer uid check); `claude stop` verifies identity by argv tail, pid, process start and the lock; a client dying before writing a state update loses it; `state.json` may be written concurrently while detached; `./yena down|restart|rebuild` kills background work; text streamed while away is not shown on reattach; a hung runner keeps the lock until `claude stop`.
- Automated tests use fake terminal streams; real TTY behaviour needs the manual check below.

Manual TTY check (cheap model, credential only in the environment):
```
./yena sh
ANTHROPIC_MODEL=claude-haiku-5-5 npm run dev
claude chat --new
```
Then: send `hello`; ask it to read a file; press Esc mid-answer and send another message; paste several lines; try `/foo` (refused), `/help`, `/new`, `/exit`; run `claude chat` again (resumes); resize the terminal during streaming; press Ctrl+C when idle, then Ctrl+C at the main prompt (yena exits). Check the cursor is visible and typing echoes afterwards, and that `ps` shows no leftover `claude` process.

## Background chat
Setting `Keep working after exit` (Claude tab, `chatKeepRunning`, default Off). It is read when a chat opens; changing it switches the open chat at once.
- On: a chat opens in a detached runner process (`src/runner/main.ts`, started by `src/runner/spawn.ts`); yena shows it through a `RemoteChatSession`. Leaving yena (exit, closed terminal) detaches: the runner finishes the current turn, sends the queued messages only after an ok turn and exits when done. The next `chat`/`resume` start reattaches to a running runner with a notice and replays the transcript plus new events (text streamed while you were away is not shown).
- Off: the chat runs in the yena process, and leaving interrupts it as before.
- After a non-ok turn with a queue the runner lingers up to 30 minutes (`LINGER_MS`, exit reason `abandoned`) so that you can reattach; a runner nobody attached to within 10 s of start also exits.
- Permission prompts and questions are never auto-approved while detached: the runner waits, and a prompt idle for 15 minutes is cancelled. Console commands (`list_commands`, `run_command`) return `yena is closed` while detached, because the console lives in yena.
- Single-session rule: a session is active only while it works (a turn, a pending permission, or background tasks it started). Only one active chat turn or ask runs per data directory, across terminals and background (`src/sessions/turn-lock.ts`): the lock and the control socket are taken when a turn starts (`ChatSession.send`) and given back once the chat is idle again, so an idle chat in any terminal blocks nobody. A send while another session works is refused with `Another session is working right now…`; the text stays in the input (in background mode the window checks the lock before sending, and a late refusal by the runner ends the turn with that message). An idle chat ends its Claude Code process 15 s after the turn (`IDLE_CLOSE_MS`, time for the transcript and the generated title); the next message resumes the session from the transcript (`resume`), so history is never lost. `chat`, `new`, `resume`, `fork` and `rewind` wait in the waiting view (`src/ui/WaitingView.tsx`; Esc cancels) only while another session works; a working background chat is attached instead. `ask` is refused only while another session works (an idle chat open in the same yena does not block it).
- A runner holds no lock while idle: detached and idle it exits (as before); attached and idle it stays as the window's bridge, without a Claude Code process. While such a runner owns `runner.sock`, a second background chat is not started; the chat runs in that yena instead (the usual fallback warning).
- Files in `/tmp/yena-claude-<uid>/session/` (0700, owner-checked): `session.lock` (only while a turn or an ask runs; JSON `{v, pid, procStart, kind: chat|ask, where: local|runner, sessionId?, startedAt, socket?}`, at most 4 KiB, created exclusively; a lock whose pid is dead or whose start time differs is stale and removed; an unparseable lock younger than 5 s counts as held; a symlinked lock falls back to the in-process busy flag only), `runner.sock` (chat protocol) and `control.sock` (status and stop; leftover sockets are removed by the next owner).
- Protocol (`src/runner/protocol.ts`): NDJSON frames, version 1, at most 1 MiB each, validated on both sides. Code: `src/chat/engine.ts` (the engine shared by both modes), `src/chat/handle.ts` (`ChatHandle`, what `ChatView` uses), `src/chat/remote-session.ts`, `src/runner/server.ts`, `src/sessions/{lock,control,stop,proc}.ts`, `src/clock-time.ts`.
- The runner registers no signal, `uncaughtException` or `unhandledRejection` listeners; it ends by itself, through the control socket, or by a signal from `claude stop`.

## Console tools

When core provides a command bridge (`ctx.commandBridge`, core 0.4.0+), the chat registers an in-process MCP server named `yena` with two tools: `list_commands` (read-only) and `run_command({command})`. They let Claude inspect and run yena console commands, subject to each command's `agent` policy (`safe`, `confirm`, `deny`). Code: `src/chat/console-tools.ts`.
- Confirmation lives inside the tool handler, not in `canUseTool`: the handler asks (`Run console command: <line>?`, no "always" option) whenever core requires confirmation. `canUseTool` allows the two `mcp__yena__*` tools without a prompt, so there is no double prompt. In auto mode the classifier reviews every `run_command` call first: a call it approves runs `confirm`-level commands without asking; a call it is unsure about reaches `canUseTool`, which flags the line (`createConsoleFlags`), and the handler then asks as usual. `deny`-level commands stay refused in every mode.
- Output goes through `formatRunResult`, then the chat scrub (sanitiser and credential redaction). Non-ok statuses are returned as tool errors. Logs carry only tool, status and duration.
- Timeouts: `run_command` asks the bridge for 10 minutes (`timeoutMs` 600000) and the MCP server's own tool timeout is 610000 ms, so the bridge times out first. While a command runs the chat's 5-minute silence timer is paused (it shares a hold counter with permission prompts); Esc interrupts. The command keeps the bridge busy until it settles, and a timed-out command keeps running if it ignores `ctx.signal`. The 600 s real round trip has not been run.
- The server stays when `MCP servers` is Off (that setting only controls servers from the Claude Code config). A user MCP server also named `yena` is shadowed by this one.
- Own metadata: `chat` and the `claude` command are `deny`; `claude session|tasks|mcp` are `safe`; `ping|rename|export|auth` are `confirm`; `ask|chat|new|resume|rewind|fork|copy|memory` are `deny`.
- Residual risks: a confirmed command runs with the console's rights; the confirmation shows the line as typed by the model, and a command can still do more than its name suggests; the list of commands and their output go to the Anthropic API.

## Projects

With the `project` module installed, the chat and `ask` can read the projects in `/workplace` and the stages in `/stage`, and writes there follow the project module's isolation:

- The project module is an optional dependency: `src/deps/project.ts` loads its public entry at runtime (`withProjects` in `src/config.ts`, before a chat or an ask builds its policy) and keeps structural copies of its types. Its `accessReader` is asked on every Read/Edit/Write check, so `project isolate` and `project finish` take effect in the open chat at once. claude never reads the project module's files itself. Not installed: no project roots. Installed but not loadable: every write into the md hub is refused.
- An Edit or Write under `/workplace`, `/stage` or the hub's `projects/` folder is refused ("that project is read-only in this work session") unless it lands inside an isolated project's folder, its docs folder `<hub>/projects/<name>` or one of its stages. The target is resolved through symlinks first. Inside an isolated project the usual rules apply: secret files are refused, `CLAUDE.md`/`.claude` are refused, `.`-folders and files always ask, the rest is auto-accepted in `acceptEdits`; docs folders are free like the rest of the hub.
- No state yet: nothing changes (no project roots). Unreadable or invalid state (the project module decides): the workplace is not readable and every docs folder is read-only.
- The policy hook refuses a Bash command that names the ssh-agent socket yena was started with (or its folder), `SSH_AUTH_SOCK` or `ssh-add`: a forwarded agent signs with the host user's own keys (a heuristic; git in yena repositories uses the account keys). yena's `compose.yaml` no longer forwards one; the check stays in case it comes back.
- With the `account` module (optional, loaded at runtime by `src/deps/account.ts`): its secret dirs (`secretDirsFor`: secrets and SSH keys) are denied to every file tool in `ask` and the chat (scope plus `Read`/`Edit` deny rules), and the policy hook refuses a Bash command naming the account data dir or the `account/secrets`, `account/keys` tails (a heuristic, bypassable by globbing). An installed account module that fails to load stops the chat and `ask` with an error instead of running unguarded.
- The chat settings deny `Edit` in `<YENA_DATA>/project/`; the policy hook refuses a Bash command naming the project module's data dir; `/workplace` and `/stage` are added as working directories when they exist at spawn; the chat hint names the `project` commands.
- Residual risk: Bash is not confined by isolation. In `default` mode every Bash call still asks; in `auto` mode the classifier decides.

## Credentials
Precedence: the account order (see `claude auth accounts`); a stored token is passed to the child as `CLAUDE_CODE_OAUTH_TOKEN`, a key as `ANTHROPIC_API_KEY`, a login by removing both so Claude Code uses its own. `src/accounts.ts` and `src/credentials.ts` are the only code that reads these.

Migration: the legacy `<dataDir>/.token` file is no longer read and is not migrated. If it was your only credential, run `claude auth login --token` again, then delete the old `<dataDir>/.token` yourself. A stale file stays unreadable to the model (the data dir is outside its roots).

- Login detection: from the login files in the config dir (`config/.credentials.json` with `claudeAiOauth`, or `primaryApiKey` in `config/.claude.json` for a Console login); yena reads them to keep each login in its slot and never prints or logs them. `auth logout` still asks `<runtime> auth status --json`. A login is shown as `subscription login` (claude.ai) or `API key (login)` (Console).
- `bin/claude` reads no credential files: it authenticates only through the environment variables or the Claude Code login in the config dir (whichever login account yena put there last). Stored tokens and keys are not picked up there.

- An API key is never accepted as a command argument: it would stay in the scrollback and history. `auth key` takes a file.
- Paths with spaces are not supported, because core splits the command line on whitespace.
- A subscription token (`sk-ant-oat…`) is rejected by `auth key` (`Run "claude auth login --token" or set CLAUDE_CODE_OAUTH_TOKEN instead.`); use the environment, `auth login` or `auth login --token`.
- `auth key` and `auth login` print a note when the new account is not first; `claude auth use <account>` puts it first.
- Without any credential, `ask` fails with `No credentials found. Set ANTHROPIC_API_KEY, …`.
- Keep secret files private: `chmod 600 <dataDir>/accounts.json` (`auth status` warns when it or the login file is readable by others).
- Every chat and `ask` start sets the module data dir and `config/` to 0700 (`restrictDataDirs` in `src/config.ts`; real dirs only, a failed chmod is ignored): Claude Code creates transcripts, file history and shell snapshots world-readable, and the closed dirs keep other users out. How long transcripts are kept is Claude Code's `cleanupPeriodDays` in `config/settings.json`, which the user sets.
- If `ANTHROPIC_BASE_URL` is set in your environment, the credential is sent there. It is your own environment; this is accepted.

## Policy caveat
Anthropic's documentation says that, unless previously approved, third-party developers may not offer claude.ai login or its rate limits in products built on the Agent SDK. yena now explicitly runs Claude Code's own claude.ai login (`auth login`), and also accepts a setup-token, for the owner's personal use of their own subscription; this rests on the owner's approval and the tool must not be shared or redistributed with that setup. Prefer `ANTHROPIC_API_KEY`. A one-time notice is printed by `auth status` / `ask` / `chat` when a subscription login or token is in use (`subscriptionNoticeShown` in `state.json`).

## Tool-use policy of `ask`
Layers:
- Tools allowlist: `Read`, `Glob`, `Grep`. Bash, Edit, Write, web tools, agents, skills and MCP tools are disallowed; MCP servers are not loaded.
- `disableAllHooks`.
- Permission deny rules: the credential and state files under `<dataDir>`, edits (not reads) of the `config/` directory, `.yena`, `/proc`, `~/.ssh`, `.env*`, `*.pem`, `id_rsa*`, and edits of `CLAUDE.md`, `CLAUDE.local.md` and `.claude/` in the project (the instructions come only from the hub, loaded through `additionalDirectories`; edits of the hub's `CLAUDE.md`/`SOUL.md` always ask: an `ask` rule and the policy hook's `ask`). `md/` and `config/` stay readable in `<dataDir>`.
- `canUseTool`: every path is resolved with realpath and must be inside the project (`/app`) or the md dir; symlinks leaving them are refused.
- Claude Code's login files are denied for Read, Grep and Glob: `config/.credentials.json`, `config/.claude.json` and `config/backups/**`; in the chat the `PreToolUse` hook also denies Bash commands that reference these auth files.
- At most 20 turns and a 5-minute timeout. `bypassPermissions` is never used.

Residual risks:
- Earlier session transcripts (`config/projects/**/*.jsonl`) and the prompt history (`config/history.jsonl`) are closed to Read, Glob and Grep in `ask` and the chat, so text once pasted or fetched does not come back into the context; `memory/` and `tool-results/` stay readable. Bash can still read them (in `default` mode it asks).
- The model can read any other non-denied file in `/app`, the md dir and the config dir (including agents, commands and settings). Its content goes to the Anthropic API and into session transcripts under `<dataDir>/config/projects`.
- Hiding of hidden/secret files from Grep and Glob rests partly on ripgrep and Claude Code behaviour plus best-effort deny rules.
- Bash reads of the login files cannot be fully prevented: the Bash check is a regex on the command text (credentials.json, .claude.json, config/backups) and globbing or obfuscation (`cat .cred*`, quoting tricks, backticks) bypasses it; closing that needs an allowlist or a sandbox.
- A claude.ai login leaves a long-lived refresh token on disk (`config/.credentials.json`, mode 0600); a Console login stores its API key in plain text in `config/.claude.json` and in `config/backups/`.
- The login probe relies on the undocumented shape of `auth status --json` and may write into the config dir; a revoked login still reads as signed in until Claude Code notices.
- The config dir is shared with `./yena claude code`, so a login made in either place is used by both. If `./yena claude code` runs while yena swaps logins, its token refresh can write the old account's tokens back after the swap (the next swap detects another account id and keeps it as its own account, but the slot of the swapped-out account may then hold older tokens). Do not run `./yena claude code` with a login while a chat may switch accounts. The email is printed on screen and never logged.
- Several yena processes changing accounts at the same moment (two `auth` commands, an ask and a switch) can lose one of the `accounts.json` updates (each write is atomic, the read-modify-write is not).
- The per-organisation caches in `.claude.json` (model access, defaults) stay from the previous account until Claude Code refreshes them.
- Env files: `claude ask` denies `**/.env*` outright. The chat's settings rules name only `**/.env` (they cannot express exceptions); the policy hook and the permission bridge refuse every other `.env*` name in every mode, except templates (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`, also `.env.<x>.example`; `ENV_TEMPLATE` in `src/policy.ts`), which the chat may read and write like any other dotfile (asked for at the top of the project). Secret names (`isSecretName`): `.env`, `.envrc`, `.env.<x>` / `.env-<x>` / `.env_<x>`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `.netrc`, `.npmrc`, `.pgpass`, SSH private keys `id_rsa`/`id_dsa`/`id_ecdsa`/`id_ed25519*`; not secrets: the env templates, `*.d.ts` (e.g. `.env.d.ts`) and public keys `id_*.pub`. The chat's settings rules name only `**/.env` and `**/id_rsa`; `claude ask` keeps the broad `**/.env*` and `**/id_rsa*`. Glob patterns and Grep `glob`s that are absolute or contain `..` are checked by the folder before their first wildcard (`globBase`), so `/app/src/**/*.ts` is allowed and `/etc/*`, `/**`, `*/../..` and `~/…` are refused.

Process lifetime (also for `chat`): a normal exit, timeout or cancel stops the `claude` child process. After SIGTERM or SIGKILL of the yena process the `claude` child can outlive it for a few seconds and exits when its stdin closes; it is not guaranteed, and a generation in progress may keep running until then (no signal handlers on purpose, so the host's signal behaviour is unchanged).

## Logging
The module logs through the host logger (`host.log`, scope `claude`) into `<YENA_HOME or cwd>/logs/yena.log` (JSON lines; format, levels, rotation and redaction are described in the host `CLAUDE.md`). On a host without `host.log` it uses a local noop logger (`src/log.ts`) and nothing is written.

Records (level, message, fields):
- info `plugin loaded`.
- info `auth status` {kind, source, accounts, limited}; info `auth accounts` {count, limited}; info `auth order|use` {count}; info `auth remove` {login}; info `account limited` {reason, next (boolean)}; info `account switched` {reason, switches}; info `claude login started` {method, sso, email (boolean)}; info `claude login finished` {exitOk, loggedIn, method, subscriptionType}; info `claude logout` {ok, stillLoggedIn}; info `api key stored`; info `stored credential removed` {removed}.
- warn `no credential` (ask and chat); info `credential resolved` {kind, source} (ask).
- info `ask started` {fresh, promptChars}; info `ask finished` {outcome, ms, model, numTurns, session8}; warn `ask failed` {outcome (`timeout`|`error`), ms, errClass, reason}; warn `ask timed out` {timeoutMs}; error `sdk load failed` {missingModule, err}.
- warn `result error` {subtype, authFailed}; warn `query threw` {errClass, aborted}.
- info `chat starting` {fresh, kind, source, resuming, model} (`model` is the chosen id or `default`); info `chat setting set` {key, value}; error `chat dependencies failed to load` {missingModule, err}; info `chat closed` {ms, session8, model}.
- info `sdk session spawned` {resuming}; info `turn started` {chars} (or {origin: 'claude-code'} for a turn Claude Code started); info `first output` {ms, warm}; info `turn aborting` {outcome}; info `turn ended` {outcome, ms, reason?, calls?, cacheWrite?, cacheRead?, output?, agentCalls?, agentCacheWrite?, agentCacheRead?, agentOutput?}; warn `turn lock busy for a Claude Code turn`; warn `sdk stream threw` {errClass}; warn `sdk stream ended unexpectedly` {authFailed}; warn `authentication failed`; warn `interrupt grace expired; recycling` {graceMs}; warn `session recycled`.
- warn `state write failed` {code}; warn `process status write failed` {err} (once per chat), warn `process status remove failed` {err}; warn `exit hook aborting requests` {count}.
- info `session lock` {action: acquired|released|stale-removed, kind, where}; info `session stop` {where, via: socket|signal, ok}; info `runner spawned` {ms}, `runner attached`/`runner detached` {keep}, `runner exit` {reason, turns, ms}; info `chat remote` {action: spawned|attached|detached, running}; warn `chat remote` {action: lost|fallback}; warn `runner spawn failed`, `runner protocol error`, `runner frame failed`, `runner request failed`, `runner server error`, `runner open failed`, `control request failed`, `control server error`, `control stop failed`, `chat remote write failed`, `chat remote state update failed`, `queue flush failed`, `engine warning`, `initial mode rejected`; info `queue flushed` {count}, `chat closed` {ms}: metadata only.
- warn `shell tmp unavailable` {error class}; debug `shell view` {shown, calls, ms, outputBytes, bound (`file`|`task`), fallback (`busy`|`focus`|`ambiguous`|`nofile`|`tmp`)}: metadata only.

`reason`/`err` values are scrubbed with the credential redactor and clipped to 300 characters.

Never logged: the prompt (only its length), assistant text, tool arguments and results, file contents, the environment, the credential or any part of it.

`registerLogRedaction` (`src/credentials.ts`) adds an exact-value redactor for the resolved credential to the logger (once per credential, keyed by a SHA-256 digest) before `credential resolved` and every later record, in addition to the host's built-in patterns. `credentials.ts` stays the only code that reads credential names and files.

## Claude Code wrapper
`./yena claude code` (from the host repo) runs `bin/claude`, unchanged by the `ask` work; it reads no credential files (see Credentials). Its `GUARD` and `HINT` strings are kept in sync with `src/config.ts` by a test. `bin/install` refreshes Claude Code in `.runtime/`, and installs the module dependencies (the Agent SDK pinned to 0.3.302, matching the runtime) when the installed SDK version differs from the pin.

## Development
From `modules/claude`: `npm install && npm run typecheck && npm test` (`npm test` runs the `.ts` and `.tsx` tests under `tests/`; `typecheck` also checks them via `tests/tsconfig.json`). `tsc` and `tsx` still come from the host's `node_modules` and types are imported from the host's `src/api.ts`, so this only works inside the host tree. The SDK and its peers are installed in the module's own `node_modules`. Tests fake the SDK. `ink` and `react` come from the host (`/app/node_modules`) and must not be added to this module's dependencies. Every `.tsx` file must start with `import React from 'react'`: yena runs tsx from `/app`, where the module's JSX settings do not apply, and `npm test` (cwd = the module) would not notice. `tests/ui/runtime.test.ts` renders the UI components in a subprocess started from the host root to catch this (on failure it reports a missing frame text, not the `ReferenceError`). From the host root, `npm run typecheck:modules` and `npm run test:modules` run these for every module.

Manual live check: use a throwaway session and a cheap model, with the credential only in the environment and never printed:
```
./yena sh
ANTHROPIC_MODEL=claude-haiku-5-5 npm run dev
claude ask hello
claude new
```

## Host-side steps
- `./yena rebuild` (or recreate the container) so the image has `ripgrep` and the container gets `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` from the host environment. These variables also reach `./yena claude code`, where they are the only credential besides a Claude Code login.
- Commit the module changes in this repo, and `Dockerfile` / `compose.yaml` in the host repo.
- `npm install --prefix` on a completely fresh clone through `bin/install` has not been tested end to end.

## Permissions that persist
"Always" for a Bash command or an MCP tool (`mcp:<tool>`) is saved in `state.json` (`allowedCommands`, at most 200) and applies to later chats; the `Permissions` settings tab (shown when there are rules) lists them, and choosing Remove drops one (also from the open chat). MCP tool calls always ask unless allowed this way (auto mode: the classifier decides first); their prompt shows the tool and its JSON arguments.
