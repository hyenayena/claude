# claude
Claude Code integration for yena. It requires chat 0.3.0: the chat contract (the events, session and permission-request types, the plan, limit and tier shapes, the turn statistics, diff previews and usage meter, the canonical tool names, and the provider API it registers with: `registerChatProvider`) through `src/deps/chat.ts`, and the chat UI (views, transcript, markdown, tool and file cards, galleries) through the lazily loaded `src/deps/chat-ui.ts`; the chat's UI is described in the chat module's README. The runner protocol (version 1) carries the contract shapes unchanged.

It is a yena plugin (`runtime: "node"`, `entry: src/index.ts`, version 0.32.0): the host loads it at startup and adds the `claude` command. It requires core 0.4 (0.13.0 or later for the fixed agent panel, 0.22.0 or later for the plan widget's `checklistRows`) and core 0.16.0 or later for `ctx.caller`: an older core has no caller, so every assistant-run `claude start` is treated as unattended and runs on an API key only.

Naming in the UI: the assistant is yena, Claude Code is the engine it runs on. Text where the assistant acts says yena ("yena is still answering", "Question from yena", plan mode, the chat settings, the `## yena` heading of `claude export`, the console caller `[yena]`, the settings tab `Chat`). Text about the tool itself keeps its name: Claude Code and its commands, the Agent SDK, Claude accounts and logins, `Claude request failed`, the `claude` command. It requires core 0.4.0+ for the console tools and core 0.5.0+ for the live Bash panel (`MountOptions.activity`, kit `OutputTail`) and core 0.5.1+ for Markdown tables (kit `styledCells`; a named import, so the module fails to load on an older core) and core 0.18.0 for file cards (kit `renderDiffCard`, `FrameRow.styled`, named imports as well) and core 0.19.0 for tool rows (kit `statusRow`, `ruledRows`, `paintTokens`, `formatElapsed`, named imports as well) and core 0.20.0 for assistant text (kit `renderCodeFrame`, the tones `heading`, `link`, `code.inline` and the glyph `wrap`, named imports as well) and core 0.21.0 for the status bar (kit `segmentBar`, `meterBar`, the tone `running`, the glyphs `meterOn`, `meterOff` and `branch`, named imports as well) and core 0.6.0+ for the chat spinners (kit `SPINNERS.sparkle`, `SPINNERS.blink`; the chat view fails to render on an older core); older cores work without them (core is declared in `yena.json`, without a version): text helpers and UI pieces come from core's public kit, imported only through `src/kit.ts` and `src/ui/kit.ts`; the md hub's path and folders come from md's public entry through `src/deps/md.ts`; `ping` and `ask` never load React, Ink or the kit UI. `claude ask` and `claude chat` run the Claude Agent SDK in a read-only mode.

## Commands
- `claude ping` — prints `pong`; confirms the module is loaded.
- Help: core generates it (`help claude`, `claude help`, `claude auth help`, hints with a description per argument and option), so the module has no `help` subcommand of its own. Claude Code's own `/help` stays reserved in the chat. Every subcommand has argument and option docs; Claude Code passthrough commands get a generated usage and argument docs (Claude Code's argument hint becomes the argument's description).
- `fix` — top-level command (`agent: deny`): after dev mode failed to start the working copy (the host's `PluginHost.devFailure` record), starts a new chat like `claude start` whose first message carries the recorded error as an indented data block and the repair steps (`project isolate`, a headless start of the working copy, `dev check`, fix, report); `src/fix.ts`. Without a record it prints `Nothing to fix: the last dev start succeeded`; on a host without the field it says to update the host. Like `claude start` it needs a chat view, so it works in the UI, not from `./yena fix`.
- `claude ask [--new] <text>` — asks Claude, continuing the last session. `--new` starts a fresh session. Use `--` before text that starts with `--`. Text starting with `/` is rejected. Only one ask runs at a time; an ask is cancelled after 5 minutes. An ask from an unattended caller (the scheduler; any run with `ctx.signal` whose `ctx.caller` is not `yena`) runs only on an API key account, as `start` does. Output ends with a footer:
  ```
  Asking yena…
  <answer>
  [session d503c507 · model claude-haiku-5-5 · subscription token]
  ```
- `chat [model]` — top-level command: opens a new chat (fresh session) with `model` or, without it, the chat model from the settings. It has `autostart: true`, so core opens it at startup, and it contributes the `Claude` settings tab, stored in `state.json` (unset keeps the Claude Code default): `Permission mode` (`chatPermissionMode`: Default, Accept edits, Auto), `Chat model` (`chatModel`: Default, Fable 5.1, Opus, Sonnet, Haiku), `Effort` (`chatEffort`: low…max, SDK `effort`), `Thinking` (`chatThinking`: Adaptive or Off, SDK `thinking: {type: 'disabled'}`), `Fast mode` (`chatFastMode`, settings flag `fastMode`), `Output style` (`chatOutputStyle`: Explanatory or Learning, settings flag `outputStyle`), `MCP servers` (`chatMcp`: On by default, servers from the Claude Code config; Off keeps `strictMcpConfig`), `Settings hooks` (`chatHooks`: Off by default; On sets `disableAllHooks: false`; yena's policy hook runs either way), `Keep working after exit` (`chatKeepRunning`: Off by default, see "Background chat"), `Input mode` (`chatInputMode`: Normal or Vim). MCP and hooks apply to new chats. All of them apply to the open chat at once (`Query.setModel`, `setMaxThinkingTokens`, `applyFlagSettings` for effort, fast mode and output style; a respawned query gets them in its options) and to new chats. Code: `src/chat-prefs.ts`. A model argument must match `[A-Za-z0-9][A-Za-z0-9._[\]-]*` (at most 100 chars) and is used for that chat only.
- `claude chat [--new]` — opens an interactive streaming chat (see below). Continues the last session; `--new` starts a fresh one. Uses the chat model from the settings.
- `claude new [model]` — opens a new chat, like `chat [model]`.
- `claude resume [session]` — continues an earlier chat of this project. Without an argument a list opens in the console (newest first: Claude Code's title or the first prompt, age, number of prompts; ↑↓, Enter resumes, Esc closes); with an argument the session whose id starts with it is resumed. The resumed chat shows its last 40 prompts and answers (text only, tool calls left out), read from `config/projects/<project>/<session>.jsonl` (`src/chat/history.ts`).
- `claude rewind` — a list of your messages in this chat (newest first); picking one restores the files Claude changed since then (Claude Code file checkpoints, `enableFileCheckpointing`, `Query.rewindFiles`) and reopens the chat on a branch from just before it (`forkSession` + `resumeSessionAt`), with that message back in the input. Rewinding to the first message opens a fresh chat.
- `claude fork` — continues the current (or last) chat on a new branch; the original stays as it was.
- `claude rename <name>` — names the chat (a `custom-title` entry in the transcript, as Claude Code's /rename writes); the bar shows it.
- `claude export [file]` — writes the chat's prompts and answers as Markdown, by default to `<dataDir>/exports/<date>-<session8>.md`; a given path must be inside the project or the data directory and must not exist yet.
- `claude copy [N]` — puts Claude's last (or Nth last) answer on the terminal clipboard (OSC 52 through core's `ctx.copyToClipboard`; at most 50 000 characters; the terminal must allow OSC 52).
- `claude memory [file]` — opens `CLAUDE.md` (or another md file in `md/`) in `$VISUAL`/`$EDITOR`/`vi` through the terminal handoff.
- `claude tasks` — the chat's tasks (background Bash, subagents) with status and age; picking a running one stops it (`Query.stopTask`).
- `claude mcp [reconnect <server>]` — status of the chat's MCP servers (after its first message), or reconnects one.
- A new chat starts on a clean screen (core clears its transcript when a chat view mounts).
- `claude code [args…]` — runs `<module>/bin/claude` (Claude Code) in your terminal via `ctx.suspend` (no shell; agent policy `deny`). Errors: no terminal hand-over (`"claude code" needs an interface that can hand over the terminal`), wrapper missing (`Run modules/claude/bin/install.`), non-zero exit (`Claude Code exited with status N`; exit 1 from the terminal, in the UI it waits for Enter first). Logs only the argument count and status. Limits: core re-splits the line on whitespace (`./yena claude code -p "a b"` becomes `-p a b`), 4096 chars, no control characters; workarounds: pipe the prompt, or run `modules/claude/bin/claude` inside `./yena sh`. The first run may self-update (~12 s).
- `claude sessions` — shows the running chat or ask, in any yena or in the background (kind, where, session, since when). Safe for the assistant.
- `claude stop [session]` — stops the running chat or ask. For a background chat it first asks the runner over its control socket, then sends SIGTERM and SIGKILL, but only to a process verified as our runner (argv ends with `src/runner/main.ts`; pid and process start time match the lock). A chat in another yena cannot be stopped from here (close that yena). Needs confirmation when the assistant calls it.
- `claude session` — prints `Session`, `Model`, `Chat model`, `Claude Code runtime`, `Agent SDK` and `Binary in use` (`runtime` or `bundled`).
- Accounts, chosen per turn (`src/accounts.ts`): the pinned account (`claude auth use`) when it is usable, else the first usable account in the order (`claude auth order`). yena never switches accounts on its own. A usage limit or billing error ends the turn with the usual message and reset time (see Limits and context); there is no switch to another account, no resend, and no return to a higher-priority account later. No limit is recorded anywhere, so a new chat or `ask` after a limit starts on the first usable account again. One subscription per session (`src/session-accounts.ts`): a session, with its resumes, forks, rewinds and `ask` follow-ups, uses at most one Claude subscription for its whole life. The first subscription a session runs on is recorded in `<dataDir>/session-accounts.json` (`{v: 1, sessions: {<id>: {account, email?, at}}}`, 0600, the latest 1000; the login also by its email, so a login to another plan counts as another subscription). A session may move to an API key at any time (billed per use); a pin or order that would put it on another subscription is not followed: the chat stays on its own subscription and says once `This chat stays on the Claude subscription "X": a chat uses only one subscription. Start a new chat ("claude new") to use "Y".` When its subscription is gone (signed out, another login, variable unset) and no API key is chosen, the chat does not start: `This chat runs on the Claude subscription "X", which is not available now…`. Sessions from before this rule are recorded at their next use. The chat changes account only when the user changes the pin or the order (within this rule): a warm process moves at its next send with no background tasks drops the process and starts a new one in the same session (never mid-turn; a steering message or a turn Claude Code starts itself is not checked). If the process is busy the move waits. The notices are `Now on account "X" (chosen with "claude auth use").` when the pinned account is taken, and `Now on account "X" instead of "Y".` otherwise. The pin is kept in `auth.json` (`pin: {name}`, validated on read, dropped on save when its account is gone or unusable). The status bar shows `*name` while the chat runs on the pinned account and `current -> *name` from the moment it is pinned until the chat moves to it at the next turn (`src/chat/pin-watch.ts`, refreshed on account and turn-end events and after `auth use|auto|remove`; a pin cleared by a runner shows at the next event). `auth status` prints a `Pinned:` line and `*` before the pinned name.
  - Accounts: `env-key` / `env-token` (`ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` from the environment; part of the order, not removable), the login `login` (below) and API keys stored in the account module (kind `anthropic-key`, read through the host's credential channel; claude stores no secret). Stored keys need `account grant claude` (only you can run it); until then, or without the account module, only the environment variables and the login work, and `auth status` says why. Default order (before any `order`): environment, the login, then stored keys in the order they were added. Accounts disabled in the account module, named like an environment account or without a secret are listed with the reason and never used.
  - Login: Claude Code's own login in its config dir (`config/.credentials.json`, written by Claude Code only, mode 0600, denied to the model) is the account `login`. It is present when that file is a non-empty regular file (`loginPresent`; yena never opens it). Its email and method (subscription or Console) come only from Claude Code's own `auth status --json` probe (`probeLogin`, cached for 60 s and refreshed after `auth login`, `auth logout` and `claude code`). The CLI uses it from its own config; yena passes no credential for it. yena stores, copies, refreshes and swaps no claude.ai login and no subscription token. `CLAUDE_CODE_OAUTH_TOKEN` from the environment is passed to Claude Code as it is: yena checks that it is set and never reads or copies its value.
  - State: `<dataDir>/auth.json` (0600) holds only the order and the pin (`{v: 1, order, pin?, migrated?}`); no secret and no limit. Names in the account module are up to 32 lowercase letters, digits, `_`, `-`.
  - Migration (one time, idempotent): when the account module loads it removes its stored subscription tokens and claude.ai logins with their secrets, drops them from the grants and writes the counts to `retired.json` (`src/retire.ts` there). The old per-module files of claude (`<dataDir>/accounts.json`, `accounts/<name>/login.json`, `credentials.json`) are read once: their API keys are created in the account module, read back and compared, and then the files are deleted; their tokens and logins are dropped, never moved. Any error leaves the files untouched and it is retried. `auth.json` of 0.20.0 is rewritten (`installed` becomes `login` in the order and the pin; `limits` and `pin.only` are dropped). The config dir is never touched by the migration. Once, `claude auth status`, `ask`, the chat start, `auth add` or `auth login` shows what was removed (`retiredNoticeAt` in `state.json`).
  - The background runner has no channel of its own: the yena it is attached to pushes the stored API keys to it over its private socket (a `credentials` frame, sent on attach and on every change); it sees the login in the shared config dir. Account changes (`auth add|remove|…`) are made in yena.
- `claude start <message…>` — opens a new chat and sends it the message (the open chat is saved and can be resumed). Policy `confirm`, so an assistant (with the user's approval) and the scheduler (`scheduler add … cmd claude start …`) can use it; run by the assistant it always asks the person, even in auto mode and with a saved "always" (`alwaysAsk` in `console-tools.ts`), so a chat never starts another chat without a human, whatever the account; it returns once the chat is up. Run by them, it shows the chat in the main area through the context of the chat's own command (`chat`, autostart); refused while a chat is answering. A start by an unattended caller (the scheduler; any run with `ctx.signal` whose `ctx.caller` is not `yena`, which is the chat's own console tools; a caller missing on an older core) runs only on an API key account: the pinned account when it is one, else the first API key account in the order. Without one the job fails with `A chat started by the scheduler runs only on an API key: Claude subscription plans are for your own interactive use. Add one with "claude auth add" or set ANTHROPIC_API_KEY.` and no chat is opened. A chat the user starts keeps the account selection of the Accounts section. The API-key-only flag stays for the life of that chat, also when the user types into it.
- `claude send <message…>` — sends the message to the chat that is open, as if typed there (into the running turn while it answers, or queued when that is refused; refused past the queue limit). With no chat open it starts one, as `claude start`. Policy `confirm`; run by the assistant it always asks, like `start`. The task form's "Save and discuss" uses it. From an unattended caller the send into an open chat is refused unless that chat was started API-key only (e.g. by a scheduled `claude start`), with the same message as for `start`; a chat the user opened is refused even while it runs on a key, since it may move to the login at its next turn.
There are two ways to get an account: `auth login` (Claude Code's own browser sign-in; yena stores nothing, the login is the account `login`) and `auth add` (paste an API key into yena; it is stored in the account module, `account list` shows it, `account show <name>` its state). No file is made by hand.
`auth` and `mcp reconnect` are real nested subcommands with their own agent policies: `auth status`, `add`, `order`, `use`, `auto`, `remove` and `logout` are `confirm` (`status` too, deliberately), `auth login` is `deny`; `mcp reconnect` inherits `safe` from `mcp`.
- `claude auth status` — the active credential (for example `Active credential: Claude Code login (subscription)` or `Active credential: account "work": API key (stored in the account module)`), then the accounts in order as a table: `▸` marks the one new turns use, `*` the pinned one, each row has the kind (the login as Claude Code login with subscription or Console and its email, a key, an environment variable); then the `Pinned:` line, file-mode warnings and the one-time notices (the subscription notice, the retirement notice). Names and emails are shown on screen only, never logged.
- `claude auth add [--name <account>]` — asks for an API key (`sk-ant-…`) with hidden input and stores it as an `anthropic-key` account in the account module (encrypted there). A subscription token (`sk-ant-oat…`) is refused: "Subscription tokens are no longer stored; sign in with "claude auth login", or set CLAUDE_CODE_OAUTH_TOKEN in your environment." In the app the input is core's `SecretInput` in the console panel (`src/ui/secret-prompt.tsx`); from a terminal (`./yena claude auth add`) a read without echo (`stty -echo`). The value never goes through arguments (refused), a file, the history or the log (`credential stored` {type: key}). Without `--name` it then asks for the account name, prefilled with `key` (then `-2`…): a text input in the app (`src/ui/name-prompt.tsx`, core's `TextField`), a line `Account name [key]:` on the terminal (empty keeps the suggestion, a bad or taken name asks again, up to 3 times); a typed name must be new. `--name` skips the question and replaces the value of an existing stored account with that name. The same value twice is refused before the name is asked; Esc at either prompt saves nothing. Notes when the new account is not the one used next.
- `claude auth order <account> [<account>…]` — puts these first, in this order; the others keep their order after them. `claude auth use <account>` — pins one account for new turns until `claude auth auto` (the chat, `ask` and cold starts all use it while it is usable; the order stays as it is). `--only` is refused: yena no longer switches accounts on its own, so a pin already keeps the account. `claude auth auto` — clears the pin. Unknown or unusable accounts are refused; removing the pinned account clears the pin. `claude auth remove <account>` — removes a stored API key account (the login is not removed here: `auth remove login` is refused with a hint to `auth logout`).
- `claude auth logout` — takes no arguments. Runs Claude Code's own logout when it reports a login (non-interactively, 30 s, output discarded) and warns if a login remains; otherwise it says Claude Code was not signed in. Stored API keys and environment variables stay (`auth remove <account>` removes one).
- `claude auth login [--console|--claudeai] [--sso] [--email <address>]` — hands the terminal over (core `ctx.suspend`) and runs Claude Code's own browser login with the module's config dir and without credentials from the environment. yena stores nothing: the login stays in Claude Code's config dir and shows as the account `login`; `--name` is refused ("there is one Claude Code login, account "login""). Refused while a chat is answering. Argument errors show even without a UI.
- Removed on 2026-10-28: `auth key --from-file` and `auth login --token` (both replaced by `auth add`), `auth accounts`/`auth list` (the list is in `auth status`). Removed on 2026-11-03: `auth login --name`, `auth use --only`, storing claude.ai logins and subscription tokens (`auth add` refuses `sk-ant-oat…`), and the `auth logout` that removed stored logins and tokens.

- `claude <command> [args…]` — any other name is a Claude Code command (built-in such as `compact` or `context`, a custom command from `config/commands`, a skill): it is sent to the open chat as `/<command> args` and runs there, its output appears in the chat. Without an open chat it fails with `No chat is open…`; while Claude is answering it is refused; once the session has reported its command list, names outside it are refused. Hints after `claude ` list the session's commands (with descriptions and argument hints from `supportedCommands()`), or, before the first message, the custom commands and skills found in `config/`.

Without a subcommand it shows its help (core's `claude help`); where no help is available (an autostart run) it fails with `Usage: claude <ping|ask|chat|new|resume|rewind|fork|rename|export|copy|memory|tasks|mcp|session|sessions|stop|auth|help|<Claude Code command>>`.

`<dataDir>` is `<YENA_DATA>/claude` (`/data/claude` in the container). It holds `md/`, `config/` (including Claude Code's own login files `config/.credentials.json` and `config/.claude.json`, plus `config/backups/`; only Claude Code writes them), `state.json` `auth.json` (order and pin, see the accounts above) and `session-accounts.json` (which subscription each session uses; account names and login emails, no secrets); yena stores no credential here. `md/` is a symlink to the shared hub of the `md` module, `<YENA_DATA>/md` (a dependency in `yena.json`), so instructions and Claude Code config folders are shared with other agents. The hub holds `agents/`, `skills/`, `commands/` and `output-styles/`; `config/<folder>` is a symlink to `../md/<folder>` so Claude Code finds them (`MD_LINKED_DIRS`; settings and hooks stay in `config/`, since they can run code and change permissions). The links are created when missing at the start of a chat or ask (and by `bin/claude`): an old real `md/` moves into the hub while the hub is blank, a real `config/<folder>` moves into the hub while the hub's folder is empty; otherwise they are left alone (`ensureMdLinks` in `src/config.ts`). Claude is pointed at the hub's own path (system prompt hint, `additionalDirectories`).

## Chat
`chat` and `claude chat [--new]` show the chat as core's main view (needs a core that provides `ctx.mount`; otherwise it fails with `"claude chat" needs an interface that can show views`). Opening a chat closes the open one first; a chat cannot run together with an ask (`A chat is already open`, `An ask is already running`). Unknown arguments give `Usage: claude chat [--new]` / `Usage: chat [model]`. The chat's views, keys, rendering and galleries are the `chat` module's (its README); this module owns the engine, the runner, the commands and the prompts that run before the view opens.


Permission modes: the `Permission mode` setting (`chatPermissionMode` in `state.json`) is the mode new chats start in and switches the open chat at once. Shift+Tab still cycles default → accept-edits → plan → auto for the open chat only (switching to accept-edits or auto asks for confirmation with Enter).
- `plan`: SDK `permissionMode: 'plan'`; Claude researches and proposes a plan without changing anything. When it calls `ExitPlanMode` the prompt asks to start (Yes: default mode; "Yes, and accept edits": accept-edits; No with a reason: Claude keeps planning). Plan needs no confirmation to enter. Claude Code writes the plan to `config/plans/`, the one part of the config dir Claude may write: the chat's settings deny the rest by listing its parts (`CONFIG_EDIT_DENY` in `src/policy.ts`), and the policy hook refuses any other write into the config dir, symlinks resolved.
- Read-only image (IMG-9): `withProjects` marks `imageReadOnly` when the project dir (the yena root, `/app`) is on a read-only filesystem (`isReadOnlyDir`: `access(W_OK)` gives `EROFS`, root included); Edit/Write there are class `deny-image` (`POLICY_DENY.image`, pointing to `/workplace/yena` and `project isolate yena`); reads stay allowed. The chat's cwd stays the yena root, so transcripts and `resume` keep their folder. In a project that is a yena checkout (`isYenaCheckout`: `yena`, `compose.yaml`, `src/cli.ts`; the working copy and its stages) the host-run files keep `noAutoAccept` (`yena`, `compose.yaml`, `Dockerfile`, `.dockerignore`, `package*.json`, `yena-modules.json`, `scripts/`, `modules/*/bin`, `modules/*/yena.json`, `modules/claude/src`, dot paths) even when isolated. `.yena` at the root of any project or stage is denied to file tools (a checkout's data). The host's state dir comes from `YENA_HOST_STATE` (set by the host's `cli.ts`): it is outside every root (file tools cannot reach it) and shell commands naming it are refused (`hostStateDenied`, `POLICY_DENY.hostState`; heuristic, SEC-11). Tests: `tests/image-policy.test.ts`.
- Writes: the md hub (`<YENA_DATA>/md`, at its own path) is Claude's own: Edit/Write there never ask, in any mode (class `free`; the chat settings allow `Edit(<hub>/**)`, so auto mode's classifier skips it too; secret-looking names stay denied). The hub's root `CLAUDE.md` and `SOUL.md` are not free: every session and agent loads them, so a change there would be a persistent prompt injection. Edit/Write on them always asks (class `prompt-only`, `ask` rules in the chat settings, and the policy hook answers `ask`, which forces the prompt in auto mode too). Another exception: in the hub's `agents/`, `skills/`, `commands/`, `output-styles/` and in any `.claude/` folder, the policy hook refuses an Edit/Write that adds or changes the frontmatter keys `allowed-tools`, `hooks`, `permissionMode` or `mcpServers` (near spellings included; removing them is fine), because they let later tool calls skip the prompts (`src/chat/definition-guard.ts`); the user makes such changes by hand. Bash writes are not checked. The data dir `<YENA_DATA>/claude` is closed for writes by the given and the resolved path (class `deny-locked`), including the `md` link and the `config/<folder>` links into the hub; the one exception is `config/plans/`, where plan mode writes its plan. The chat settings carry no deny rule for the `md` link or the linked `config/<folder>`s: Claude Code resolves symlinks in rule paths, so such a rule would deny the hub itself (the policy hook refuses those paths instead). When yena runs outside the container (data under `./.yena`) the `Edit(./.yena/**)` deny rule also closes the hub.
- `default`: every Edit/Write and Bash call asks.
- `accept-edits`: Edit/Write inside the project are accepted without asking (the bridge decides; the SDK stays in `default`).
- `auto`: the SDK `permissionMode: 'auto'` — Claude Code's model classifier approves or denies each tool call and only asks (through the usual prompt) when it cannot decide. A running query is switched with `Query.setPermissionMode`; a new one gets it in its options. If the SDK rejects it (account, model or version without auto mode), the chat falls back to `default` and prints `Auto mode is unavailable: <reason>`.
- The hard path policy holds in every mode: a `PreToolUse` hook (`src/chat/policy-hook.ts`, passed as the SDK `hooks` option, which `disableAllHooks` does not cover) denies reads outside the roots (Read, Glob and Grep may also read `bundled-skills/` and the session's `tasks/` in the CLI's tmp dir `/tmp/yena-claude-<uid>/claude-<uid>`, and the chat's own scratch folder, where Read, Edit and Write are free; `Scope.readRoots`, `Scope.scratch`), Edit/Write outside the project or into guarded/secret paths, and background Bash, even when the classifier approved the call. Settings deny rules still apply too. What auto mode does not limit: Bash commands inside the container that the classifier approves.


Behaviour and limits:
- One streaming query per chat; a turn ends at the SDK `result`. After an interrupt the same query is reused; if no result arrives within 8 s it is recycled and the next message respawns it with `resume`.
- Subagents: the chat tools are Read, Glob, Grep, Bash, Edit, Write, AskUserQuestion, `Agent`, `SendMessage`, `Skill`, `TodoWrite`, `TaskCreate`, `TaskUpdate`, `WebSearch` and `WebFetch`, so agents from `config/agents` (and `claude pipeline …`) run. They run in place, in the foreground or in the background (`run_in_background`); only `isolation` (worktree, remote) is denied (`src/chat/agent-policy.ts`, in the bridge and the policy hook). Starting an agent does not ask; each tool call it makes goes through the same prompts, mode and path policy. Their messages are shown in the agent panel (below). `claude ask` still has no agents.
- `Skill`, `TodoWrite`, `TaskCreate`, `TaskUpdate` and `WebSearch` run without asking (the task tools are the CLI's default todo tools: the bundled CLI offers them instead of TodoWrite, so the chat could not make a task list before; they touch only the CLI's own task store in its config dir, no user files and no network). `WebFetch` asks for every host until the user picks "Yes, always for <host>" (the prompt shows the URL and warns that it leaves the container); the policy hook makes auto mode ask for a new host too, since a URL can carry data out. Allowed hosts are kept like Bash "always" rules (`web:<host>`) and listed in the settings tab "Permissions", where they can be removed. The old checklist under the tools is gone; the plan is in the header (see the chat README). A successful plan tool call (TodoWrite, TaskCreate, TaskUpdate, TaskList, TaskGet) prints no row; a failed one prints its red reason row.
- Ctrl+B moves the running Bash commands and subagents to the background (`Query.backgroundTasks`); the status bar counts running subagents (`2 agents`, `✦ 2` when narrow; foreground or not) and background work (`1 in background`), and a settled background task prints `⚙ Background task completed: …`. When a background task ends, Claude Code starts a turn by itself to read its notification; the chat shows it as work like any other turn (`session_state_changed`, enabled with `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS`), so the idle close never ends it midway, and a detached runner waits for it (`TASK_SETTLE_MS`).
- `./yena kill` report: a chat engine (in yena or in a runner) keeps one line about its chat in `$YENA_STATUS_DIR/<pid>` (the yena script sets it): `chat <id8>: idle`, `chat <id8>: working` or `chat <id8>: working, N subagents` (running tasks of type `local_agent`; `new` before the session has an id). It is rewritten on every state, session and task event when the line changes (0600 in a 0700 folder, written to a temp file and renamed) and removed when the chat closes; without the variable nothing is written (`src/chat/process-status.ts`). `./yena kill` prints these lines for the processes it stops.
- The turn timeout counts silence: 5 minutes without any SDK message (subagent messages included) ends the turn (`Request timed out: no activity for 300 seconds`). At most 20 turns per user message (reaching it ends the turn with an error and the next message resumes).
- The session id is saved after each successful turn and also after a failed one (limit, context, timeout, cancel) once the session has started, so `claude chat` and `claude ask` continue the same session. The failed message is not restored to the draft because it is already part of the session.
- Limits and context (`src/chat/limits.ts`, which imports only the pure chat contract through `src/deps/chat.ts`, so `ask` stays free of react/ink): a usage limit prints `Usage limit reached (5-hour limit), resets at 14:30 UTC (in 1h 20m). The chat is saved; send a message after the reset to continue.` (reset time in the container's zone, UTC unless `TZ` is set, plus a relative `in Xh Ym`; without a reset time the CLI's own text is shown, capped at 200 characters). A temporary 429 prints `Rate limited by the API. Wait a moment, then send again`; `billing_error` prints `The account cannot be billed (billing_error). Check the plan or credits…`. Context overflow (`prompt_too_long`, `blocking_limit`, `rapid_refill_breaker`) prints `The conversation no longer fits in the model's context. Run "claude compact" in the console to summarise it and continue, or "chat" to start a new chat`; `ask` suggests `claude chat` then `claude compact`, or `claude ask --new <text>`. After a limit or context failure the chat stays open: the next send or `claude compact` reaches the same session, and if the stream ended the next send resumes with the saved id. Messages queued when a turn fails (limit, context, interrupt) go back into the draft. Claude Code itself auto-compacts and retries 429/529; this module only adds guidance. `ask` uses the same texts (without chat wording), redacted. A usage limit or billing error never switches to another account and never resends the message: the turn ends with this text, and the next send uses the same account unless the pin or the order changed.
- Early warning: with a subscription (OAuth) credential the CLI sends `rate_limit_event`; when its status is `allowed_warning` or `rejected` the status/title bar gets an indicator such as `5h limit 91%, resets 14:30` or `weekly limit reached, resets Oct 24, 09:00`, which disappears at the reset time. API keys produce no such events. Logs record only `failure: <kind>`, never the CLI text.
- All text shown (model output, tool arguments and results, errors, your own input) is stripped of terminal escapes and bidi/control characters first, then redacted: the Claude credentials, the stored accounts' values and `ANTHROPIC_API_KEY`, the host's own redactor (which includes the account module's values) and common secret shapes (`sk-ant-…`, `sk-…`, GitHub tokens, AWS `AKIA…`, PEM private keys). `ask` output gets the same treatment. This is display hygiene only: what Claude itself reads from a tool is not masked by yena.
- Same read-only policy as `ask` (Glob/Grep/Read). Permission prompts, Edit/Write and a diff view are a later phase.

Residual risks:
- Output escaping relies on core's kit sanitizer (`sanitizeBlock`, then this module's redaction), because Ink passes OSC/SGR/bidi sequences through.
- A view that ignores Ctrl+C cannot be interrupted; the chat handles it.
- If yena is killed by SIGTERM/SIGKILL, the `claude` child lingers until its stdin closes (a few seconds; a turn in progress may keep running until then). Closing the chat on unmount is a mitigation, not a guarantee.
- The SDK shapes of subagent messages (`parent_tool_use_id` messages, `task_started` fields, `task_updated`) are not recorded in a fixture; the panel is verified with synthetic events until a live check.
- Live Bash output depends on Claude Code's undocumented tasks directory layout: a CLI update can silently disable it (Bash itself is unaffected). Another process running as your uid could plant a file during the short window before a call is bound; the effect is limited to the panel text, which is scrubbed. The uid check and the panel's mouse/TTY behaviour are verified only with tests and fake streams (as root).
- Limit handling rests on reading the Claude Code 2.1.302 binary, not on a recorded session (no fixture): that a `rejected` event may precede the 429 and that `utilization` is a fraction. A usage limit is told from a temporary 429 only by a rejected event or the text `hit your limit|usage limit`, so changed CLI wording degrades to the rate-limit message.
- The container timezone is UTC, so reset times read in UTC unless `TZ` is set (forwarding `TZ` in `compose.yaml` and `tzdata` in the image is a host follow-up, not done).
- A new chat view shows the early warning only after its first `rate_limit_event` (the info is not shared between views).
- Background chat: a `confirm` console command is confirmed by the runner's chat with the same logic as a chat without the runner (`console-tools.ts`: auto mode runs it unless the classifier was unsure, a saved "always" covers it, otherwise the prompt goes through the chat's permission queue to the attached client); the runner then sends `bridgeRun` with `approved: true` and the client runs it without a second prompt (until 2026-10-29 the runner sent `bridgeAsk` and the client prompted for every such command, ignoring auto mode and "always"). A `bridgeRun` without `approved` that the client's bridge finds `confirm` still prompts in the client, and approval stays tied to the id. The client thus trusts the runner for console commands as it already does for Edit, Bash and the mode; a compromised same-uid runner runs as root next to the client and needs no console command to do harm. The client still answers `bridgeAsk` from an older runner. the runner trusts anything that can open its 0600 socket in the 0700 directory (no peer uid check); `claude stop` verifies identity by argv tail, pid, process start and the lock; a client dying before writing a state update loses it; `state.json` may be written concurrently while detached; `./yena down|restart|rebuild` kills background work; text streamed while away is not shown on reattach; a hung runner keeps the lock until `claude stop`.
- Automated tests use fake terminal streams; real TTY behaviour needs the manual check below.

### Model router

Chat settings "Model router" (Off by default: nothing below happens, `claude tier` is refused) and "Task classifier" (On by default, only with the router on), plus a model and an effort per tier. The Chat tab draws each tier as one row under the heading "Model tiers" (`light  → [haiku] [medium]`, needs core 0.14.0 and host 0.4.0; older cores list "Light tier: model" and "Light tier: effort" as radio lists). Tiers are provider-neutral: `light`, `standard`, `strong`, `max`. Defaults (model · effort): light = haiku · medium, standard = sonnet · medium, strong = opus · medium, max = opus · high; the effort choices are the five efforts (no "Default" entry), and choosing a tier's default stores nothing, so the tier keeps following its default. The "Model" and "Effort" settings apply when the router is off or the chat is not routed.

- Rating: with the classifier on, a one-shot SDK call (`src/chat/classifier.ts`, the light tier's model, no tools or hooks, low effort, 1 turn, timeout) rates every message and decides whether it continues the current task (rating kept, raised only) or starts a new one (new rating). The prompt is capped and carries the current rating, up to two earlier messages of the task and the tail of the last answer; the message is data, not instructions. It adds about 1-3 s per routed message. On failure the chat keeps its tier (`kept`, `failed`). `max` is rare: the classifier gives it only to very complex long-horizon planning, otherwise the user or the model escalates.
- Main chat: it moves up to the rating at once and moves down only when its prompt cache is cold (no turn for over 5 minutes, a session not yet known, or a context under about 20k tokens); otherwise it stays on the stronger tier (`held`). The switch is applied live (`setModel`, effort) with no respawn; the engine records a switch only once it was applied, so a failed, timed-out or interrupted switch is retried at the next message.
- Agents: subagents always follow the rating. Tiers are written inside the agent file's `model:` (no `tier:` key; it is skipped as an unknown key). `model: <tier>` always uses that tier; `model: a/b[/c[/d]]` is a contiguous range from the first to the last entry (strictly ascending tiers, at most 4 entries, at most one entry fully in CAPS, e.g. `standard/STRONG`). The CAPS entry is the default used without a rating (router off, or classifier off and nothing pinned); without CAPS the default is the lower entry for 2 entries and the second entry for 3-4. With a rating or a pin the tier is clamped into the range. A single CAPS entry (`MAX`) is just that tier; mixed case (`Strong`) never marks a default. A `/` value that is not tiers (`opus/max`) or any invalid form behaves like a concrete model (unchanged; debug log `agent tier invalid`); concrete models, `inherit` and no `model:` are unchanged. Tier-syntax agents are translated also with the router off, because Claude Code reads `model:` itself and does not understand tiers (plain Claude Code without yena does not understand the syntax; accepted). Two mechanisms: the PreToolUse hook rewrites the Agent call's `model` and `effort` with `updatedInput` (`agent-route.ts`; it reads name and model leniently, so a file the strict reader skips is still routed; verified live on SDK 0.3.302), and tier-syntax agents also get a programmatic `AgentDefinition` at their default tier (`agent-defs.ts`, built at open and rebuilt on every send; the `agents` option is passed whenever it is non-empty) only when the frontmatter maps faithfully (allowlist: name, description, tools, disallowedTools, model, effort, color, maxTurns, skills, memory, background; any other key, multi-line YAML, an unparsable value or a file over 64 KiB means no definition, the hook covers it). A project agent skipped by the strict reader still shadows a hub agent of the same name. `canUseTool` `updatedInput` is ignored by Claude Code for the Agent tool, so the bridge does not rewrite.
- Display: a routed message shows `Routing…` like a running tool (only when the classifier actually runs), then `Routing(<tier>) · <detail>` (`chat standard -> strong`, `new task`, `kept`, `held (chat strong)`, `pinned`, `failed, model unchanged`); the status bar shows the task rating and `chat: X` when the chat tier differs. Pinned messages print `Routing(max) · pinned`. A route cut short by an interrupt keeps the rating in the bar.
- `claude tier [auto|light|standard|strong|max]`: pins the open chat to a tier (a pin set during rating wins) until `claude tier auto` or a new chat; without an argument it shows the state. With the classifier off, pins and agent ranges still work. The command is agent `confirm` and always asks, even in auto mode and with a saved "always" (`alwaysAsk` in `console-tools.ts`); the chat hint tells the model it may ask for `claude tier max` when a task is stuck.
- Runner: `route-start` and `route` events and the `setTier` frame cross the runner like other events (`runner/protocol.ts` validates tiers and outcomes).
- Residual risks: the programmatic definition's precedence over a same-named file is unverified live (the hook rewrites the model anyway); the classifier is a second Claude Code process on the same login; per-message effort for the main chat is not done.

## Background chat
Setting `Keep working after exit` (Chat tab, `chatKeepRunning`, default Off). It is read when a chat opens; changing it switches the open chat at once.
- On: a chat opens in a detached runner process (`src/runner/main.ts`, started by `src/runner/spawn.ts`); yena shows it through a `RemoteChatSession`. Leaving yena (exit, closed terminal) detaches: the runner finishes the current turn, sends the queued messages only after an ok turn and exits when done. The next `chat`/`resume` start reattaches to a running runner with a notice and replays the transcript plus new events (text streamed while you were away is not shown).
- Off: the chat runs in the yena process, and leaving interrupts it as before.
- After a non-ok turn with a queue the runner lingers up to 30 minutes (`LINGER_MS`, exit reason `abandoned`) so that you can reattach; a runner nobody attached to within 10 s of start also exits.
- Permission prompts and questions are never auto-approved while detached: the runner waits, and a prompt idle for 15 minutes is cancelled. Console commands (`list_commands`, `run_command`) return `yena is closed` while detached, because the console lives in yena.
- Single-session rule: a session is active only while it works (a turn, a pending permission, or background tasks it started). Only one active chat turn or ask runs per data directory, across terminals and background (`src/sessions/turn-lock.ts`): the lock and the control socket are taken when a turn starts (`ChatSession.send`) and given back once the chat is idle again, so an idle chat in any terminal blocks nobody. A send while another session works is refused with `Another session is working right now…`; the text stays in the input (in background mode the window checks the lock before sending, and a late refusal by the runner ends the turn with that message). An idle chat ends its Claude Code process 15 s after the turn (`IDLE_CLOSE_MS`, time for the transcript and the generated title); the next message resumes the session from the transcript (`resume`), so history is never lost. `chat`, `new`, `resume`, `fork` and `rewind` wait in the waiting view (`src/ui/WaitingView.tsx`; Esc cancels) only while another session works; a working background chat is attached instead. `ask` is refused only while another session works (an idle chat open in the same yena does not block it).
- A runner holds no lock while idle: detached and idle it exits (as before); attached and idle it stays as the window's bridge, without a Claude Code process. While such a runner owns `runner.sock`, a second background chat is not started; the chat runs in that yena instead (the usual fallback warning).
- Files in `/tmp/yena-claude-<uid>/session/` (0700, owner-checked): `session.lock` (only while a turn or an ask runs; JSON `{v, pid, procStart, kind: chat|ask, where: local|runner, sessionId?, startedAt, socket?}`, at most 4 KiB, created exclusively; a lock whose pid is dead or whose start time differs is stale and removed; an unparseable lock younger than 5 s counts as held; a symlinked lock falls back to the in-process busy flag only), `runner.sock` (chat protocol) and `control.sock` (status and stop; leftover sockets are removed by the next owner).
- Protocol (`src/runner/protocol.ts`): NDJSON frames, version 1, at most 1 MiB each, validated on both sides. The optional additions keep version 1: the UI event `context` (`{used, limit?}`, also the snapshot's `context`), the UI event `plan` (`{items}`, at most 50 items with `content`, `activeForm?`, `id?` of at most 32 characters and `status` `pending|in_progress|completed`; the reader caps each text at 400 UTF-16 units, while the sender clips to 200 code points) and the snapshot's optional `plan` (the same shape), and `turn-end.summary` (capped in `readTurnSummary`: 200 files, paths of 1024 characters, counts up to 10^9). A client drops an `event` whose UI kind it does not know; an older client fails on the `context` kind, so a newer runner needs a newer client (as with `agent-message`). Code: `src/chat/engine.ts` (the engine shared by both modes), `src/chat/handle.ts` (`ClaudeChatHandle`, what `ChatView` uses), `src/chat/remote-session.ts`, `src/runner/server.ts`, `src/sessions/{lock,control,stop,proc}.ts`, `src/clock-time.ts`.
- The runner registers no signal, `uncaughtException` or `unhandledRejection` listeners; it ends by itself, through the control socket, or by a signal from `claude stop`.
- Runners started before 0.21.0 keep the old code (with account switching and the stored logins) until they stop: end them with `claude stop` or `./yena kill`. From 0.21.0 on, a chat the scheduler starts runs only on an API key account, in a runner or in yena.

## Console tools

When core provides a command bridge (`ctx.commandBridge`, core 0.4.0+), the chat registers an in-process MCP server named `yena` with two tools: `list_commands` (read-only) and `run_command({command})`. They let Claude inspect and run yena console commands, subject to each command's `agent` policy (`safe`, `confirm`, `deny`). Code: `src/chat/console-tools.ts`.
- Confirmation lives inside the tool handler, not in `canUseTool`: the handler asks (`Run console command: <line>?`) whenever core requires confirmation. Its "always" option (`Yes, always for "<command> <subcommand>"`) saves `cmd:<command> <subcommand>` (canonical names from the bridge; `cmd:<command>` without one), and later lines of that command run without a prompt whatever their arguments, in auto mode also when the classifier flagged them. Not offered, and saved rules not used, in plan mode and for every `claude auth …` line (`neverAlways`). `<subcommand>` can be a nested path (`stage make`); a key saved earlier for the parent (`cmd:project stage`) does not cover the nested paths, they ask again. `canUseTool` allows the two `mcp__yena__*` tools without a prompt, so there is no double prompt. In auto mode the classifier reviews every `run_command` call first: a call it approves runs `confirm`-level commands without asking; a call it is unsure about reaches `canUseTool`, which flags the line (`createConsoleFlags`), and the handler then asks as usual. `deny`-level commands stay refused in every mode.
- Output goes through `formatRunResult`, then the chat scrub (sanitiser and credential redaction). Non-ok statuses are returned as tool errors. Logs carry only tool, status and duration.
- Timeouts: `run_command` asks the bridge for 10 minutes (`timeoutMs` 600000) and the MCP server's own tool timeout is 610000 ms, so the bridge times out first. While a command runs the chat's 5-minute silence timer is paused (it shares a hold counter with permission prompts); Esc interrupts. The command keeps the bridge busy until it settles, and a timed-out command keeps running if it ignores `ctx.signal`. The 600 s real round trip has not been run.
- The server stays when `MCP servers` is Off (that setting only controls servers from the Claude Code config). A user MCP server also named `yena` is shadowed by this one.
- Own metadata: `chat` and the `claude` command are `deny`; `claude session|tasks|mcp` (and `mcp reconnect`) are `safe`; `ping|rename|export` and `auth status|add|order|use|remove|logout` are `confirm`, `auth login` is `deny`; `ask|chat|new|resume|rewind|fork|copy|memory` are `deny`.
- Residual risks: a confirmed command runs with the console's rights; the confirmation shows the line as typed by the model, and a command can still do more than its name suggests; the list of commands and their output go to the Anthropic API.

## Projects

With the `project` module installed, the chat and `ask` can read the projects in `/workplace` and the stages in `/stage`, and writes there follow the project module's isolation:

- The project module is an optional dependency: `src/deps/project.ts` loads its public entry at runtime (`withProjects` in `src/config.ts`, before a chat or an ask builds its policy) and keeps structural copies of its types. Its `accessReader` is asked on every Read/Edit/Write check, so `project isolate` and `project finish` take effect in the open chat at once. claude never reads the project module's files itself. Not installed: no project roots. Installed but not loadable: every write into the md hub is refused.
- An Edit or Write under `/workplace`, `/stage` or the hub's `projects/` folder is refused ("that project is read-only in this work session") unless it lands inside an isolated project's folder, its docs folder `<hub>/projects/<name>` or one of its stages. The target is resolved through symlinks first. Inside an isolated project the usual rules apply: secret files are refused, `CLAUDE.md`/`.claude` are refused, `.`-folders and files always ask, the rest is auto-accepted in `acceptEdits`; docs folders are free like the rest of the hub.
- No state yet: nothing changes (no project roots). Unreadable or invalid state (the project module decides): the workplace is not readable and every docs folder is read-only.
- The Bash text checks of the policy hook (auth files, account secrets, host state, project data, process environments, ssh-agent) match the command text, so they also refuse a command that only mentions a name (a heredoc writing a test, a grep or sed pattern). Their messages end with `BASH_TEXT_NOTE`: write such files with Edit or Write and search with Grep, which check the real path. This sends the model to a tool that enforces the same rule instead of a workaround; the read denies themselves are the sandbox's (`denyRead`).
- The policy hook refuses a Bash command that names the ssh-agent socket yena was started with (or its folder), `SSH_AUTH_SOCK` or `ssh-add`: a forwarded agent signs with the host user's own keys (a heuristic; git in yena repositories uses the account keys). yena's `compose.yaml` no longer forwards one; the check stays in case it comes back.
- With the `account` module (optional, loaded at runtime by `src/deps/account.ts`): the paths its `deniedPathsFor` gives (everything in the account data dir except `ssh_config`: secrets, keys, the vault folder with its key, the grants file, the accounts and kinds files; denied as a file and as a folder) are denied to every file tool in `ask` and the chat (scope plus `Read`/`Edit` deny rules), and the policy hook refuses a Bash command naming the account data dir or the `account/secrets`, `account/keys` tails (a heuristic, bypassable by globbing). An installed account module that fails to load stops the chat and `ask` with an error instead of running unguarded.
- The chat settings deny `Edit` in `<YENA_DATA>/project/`; the policy hook refuses a Bash command naming the project module's data dir; `/workplace` and `/stage` are added as working directories when they exist at spawn; the chat hint names the `project` commands.
- Bash sandbox (SEC-12, `src/chat/sandbox.ts`): the chat runs Bash in Claude Code's sandbox (bubblewrap and socat, in the image since 2026-10-28). Claude Code lets sandboxed commands write to the working directory and every additional directory, so write denies carve out every entry of `/workplace`, `/stage` and `<hub>/projects` that is not an isolated folder (a parent of one is split, never denied whole, because a write deny wins over an allow; so the roots themselves stay writable and Bash can create a new entry there, though never change an existing project that is not isolated: an accepted risk, ENV-2), every entry of the config dir except `plans/`, and the hub's `CLAUDE.md` and `SOUL.md`; `/tmp` is writable. Read denies cover the secrets the file tools are denied (claude credentials, accounts, `state.json`, login files, transcripts and history, the account module's secret dirs, the project and host state dirs, `~/.ssh`, `./.yena`) and `/proc` (start-up environments hold credentials); `allowRead` re-opens the host's `logs/` (metadata-only JSON lines) for reading, and the policy hook lets a sandboxed command name that folder (as a whole path segment, never with `..`) while the rest of the host state stays refused; the file tools read it as a read root; nothing writes there. Credential variables: `credentials.envVars` denies `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` and `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` (`SANDBOX_DENIED_ENV`), so Claude Code unsets them before every sandboxed command and keeps them for its own API calls; `printenv` in Bash shows no key or token. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is not used: Claude Code then forces the permission mode to `default` (no auto, accept-edits or plan) and needs a full PID namespace with its own `/proc`, which this unprivileged container cannot mount. Residual: unsandboxed Bash (the fallback below), the user's own hooks and stdio MCP servers from the Claude Code config still inherit these variables. Network: `github.com`, `*.github.com`, `*.githubusercontent.com` and `registry.npmjs.org` pass, any other host asks (auto mode refuses it). `allowUnsandboxedCommands` and `autoAllowBashIfSandboxed` are off, so Bash still goes through the prompts and the policy hook. Isolation changes while a chat is open: before every Bash call the policy hook rebuilds the sandbox from the project module and, when it changed, applies it to the running query (`applyFlagSettings`); a failed update denies the command. Claude Code narrows a running sandbox at once but never widens it past the one the process started with (seen 2026-10-28: an isolate after a start without it did not reach Bash until the next spawn), so a query starts with no project denies and the first Bash call narrows it. Git over ssh signs through the account module's ssh-agents (the sandbox sets its own `GIT_SSH_COMMAND`, so the account picks the agent through the ssh config it writes, which the image includes); the Linux sandbox can only allow all unix sockets or none, so with the account module installed `allowAllUnixSockets` is on and the chat's own socket folder (`<shell tmp>/session`: `runner.sock`, `control.sock`) is read-denied instead. Any new yena socket must live in a folder the sandbox hides. At start the chat checks that `bwrap` and `socat` are on `PATH` and that bubblewrap can create its namespaces (`sandboxStarts`, a short `bwrap … true`); if not (an older image, or a container without the profile below) it warns and runs Bash unsandboxed as before, because Claude Code would otherwise fail every Bash command. Docker's default seccomp profile forbids the namespaces, so `compose.yaml` loads `seccomp.json` (Docker's default plus `clone`/`clone3` with namespace flags, `unshare`, `setns`, `mount`, `umount`, `umount2`, `pivot_root`). The container is unprivileged, so `enableWeakerNestedSandbox` is on (the container's `/proc` is bind-mounted, then read-denied; with the sandbox on, the hook's `environ` word check is off, because it also refused commands that only mention the word; it stays for unsandboxed Bash). Claude Code's sandbox leaves placeholders behind (Claude Code issue 102516), so `src/chat/sandbox-leftovers.ts` removes exactly three signatures: an empty `.claude/.cc-writes` folder (and the `.claude` folder when it is empty after that), an empty regular `.mcp.json`, and an empty, read-only `config.lock` in the `.git` folder of the enclosing repository (a real git lock is writable and stays); symlinks are never followed. It sweeps the working directory and the additional directories at chat start, and again, together with the cwd of each finished Bash call, after a Bash call ends (the Post, failure or denial hook) once no other Bash call is in flight, and logs `sandbox leftovers removed` with the count and kinds, never paths.
- Residual risks: user namespaces inside the container widen the kernel surface reachable from it (as on any host with unprivileged user namespaces). Not verified in the real container yet: how a network prompt reaches the chat through the SDK. With unix sockets open, Bash can use every enabled account's agent (sign as that account, never read the key) and reach the sockets of Claude Code's own sandbox proxy (filtered like its network). New top-level entries in the config dir or in a managed dir are denied from the next Bash call on, not before. Symlinks in the deny lists are resolved by Claude Code.

## Credentials
Precedence: the account order and pin (see `claude auth status`). The environment is read as Claude Code reads it: `ANTHROPIC_API_KEY` is passed to the child as the key, `CLAUDE_CODE_OAUTH_TOKEN` is passed through untouched (yena checks only that it is set). A stored API key is passed as `ANTHROPIC_API_KEY`; the login removes both variables from the child's environment so Claude Code uses its own. The stored keys come from the account module through `host.credentials` (`yena.json` declares `"credentials": {"anthropic-key": "write"}`; `src/vault.ts` is the adapter and keeps them in memory only, hidden from `JSON.stringify`/`inspect`). Without a usable store (no account module, an older host, no grant, a store that cannot decrypt) only the environment variables and the login work, with the reason in `auth status` and in the `No credentials found` error (`account grant claude`, `mod install account`, `account vault status`).

Subscriptions: a subscription is used only through Claude Code's own sign-in (`claude auth login`, or `./yena claude code`) or your own `CLAUDE_CODE_OAUTH_TOKEN` in the environment. yena stores no claude.ai login, no session or refresh token and no subscription token, and never switches accounts at a usage limit. Every account used must be your own (Anthropic's Consumer Terms do not allow sharing accounts). API keys are recommended for everyone. A chat started by the scheduler, or by any other unattended caller, runs only on an API key account; without one it does not start and says why.

Migration: the legacy `<dataDir>/.token` file is no longer read and is not migrated. If it was your only credential, add an API key with `claude auth add` (a subscription token is refused there: use `CLAUDE_CODE_OAUTH_TOKEN` or `claude auth login`), then delete the old `<dataDir>/.token` yourself. A stale file stays unreadable to the model (the data dir is outside its roots). Stored subscription tokens and logins are removed by the one-time migration (see Accounts).

- Login detection: `loginPresent` checks that `config/.credentials.json` is a non-empty regular file; its content is never opened by yena. Email and method come from Claude Code's `auth status --json` (`probeLogin`, cached for 60 s). A login is shown as `subscription login` (claude.ai) or `API key (login)` (Console). yena never saves, copies or logs the login.
- `bin/claude` reads no credential files: it authenticates only through the environment variables or the Claude Code login in the config dir. Stored keys are not picked up there.

- A key is never accepted as a command argument: it would stay in the scrollback and history. `auth add` asks for it with hidden input.
- `auth add` and `auth login` print a note when the new account is not first; `claude auth order` puts it first, `claude auth use` pins it.
- Without any credential, `ask` fails with `No credentials found. Run "claude auth login" …`.
- Keep state files private: `auth status` warns when `auth.json` or the login working copy `config/.credentials.json` is readable by others (`chmod 600`).
- Every chat and `ask` start sets the module data dir and `config/` to 0700 (`restrictDataDirs` in `src/config.ts`; real dirs only, a failed chmod is ignored): Claude Code creates transcripts, file history and shell snapshots world-readable, and the closed dirs keep other users out. How long transcripts are kept is Claude Code's `cleanupPeriodDays` in `config/settings.json`, which the user sets.
- If `ANTHROPIC_BASE_URL` is set in your environment, the credential is sent there. It is your own environment; this is accepted.

## Policy caveat
Anthropic's rules (code.claude.com/docs/en/legal-and-compliance, checked 2026-11-03; Consumer Terms §2 and §3) say:
- OAuth sign-in is for purchasers of Claude plans and for ordinary use of Claude Code and other native Anthropic applications. The advertised Pro, Max and Ultra limits assume ordinary, individual usage of Claude Code and the Agent SDK.
- Developers may not collect, store or intermediate Claude.ai credentials or session tokens: sign-in to a Claude account must complete through Anthropic's own flow. An end user may sign in to the unmodified Claude Code binary with their own subscription.
- Accounts are your own. Do not share credentials, and do not bypass usage systems or protective measures.

yena therefore runs the unmodified Claude Code through the Agent SDK; uses only the login Claude Code keeps itself (made with `claude auth login`, Claude Code's own flow) or your own `CLAUDE_CODE_OAUTH_TOKEN` from the environment; stores no claude.ai login and no token; never switches accounts at a usage limit; and never lets one session run on two subscriptions (see Accounts). It is for your own personal use of your own subscription: do not share or run this setup for others, and do not offer it to anyone else. For anything else use an API key (`claude auth add` or `ANTHROPIC_API_KEY`). API keys are recommended for everyone. A one-time notice is printed by `auth status`, `ask`, `chat` and `auth login` when a subscription is in use (the `subscriptionNotice` version in `state.json`; the notice shows again when its wording changes).

## Tool-use policy of `ask`
Layers:
- Tools allowlist: `Read`, `Glob`, `Grep`. Bash, Edit, Write, web tools, agents, skills, the task tools (`TaskCreate`, `TaskUpdate`, `TaskGet`, `TaskList`, `TodoWrite`) and MCP tools are disallowed; MCP servers are not loaded.
- `disableAllHooks`.
- Permission deny rules: the credential and state files under `<dataDir>` (including `auth.json`), edits (not reads) of the `config/` directory, `.yena`, `/proc`, `~/.ssh`, `.env*`, `*.pem`, `id_rsa*`, and edits of `CLAUDE.md`, `CLAUDE.local.md` and `.claude/` in the project (the instructions come only from the hub, loaded through `additionalDirectories`; edits of the hub's `CLAUDE.md`/`SOUL.md` always ask: an `ask` rule and the policy hook's `ask`). `md/` and `config/` stay readable in `<dataDir>`.
- `canUseTool`: every path is resolved with realpath and must be inside the project (`/app`) or the md dir; symlinks leaving them are refused.
- Claude Code's login files are denied for Read, Grep and Glob: `config/.credentials.json`, `config/.claude.json` and `config/backups/**`; in the chat the `PreToolUse` hook also denies Bash commands that reference these auth files.
- At most 20 turns and a 5-minute timeout. `bypassPermissions` is never used.

Residual risks:
- Earlier session transcripts (`config/projects/**/*.jsonl`) and the prompt history (`config/history.jsonl`) are closed to Read, Glob and Grep in `ask` and the chat, so text once pasted or fetched does not come back into the context; `memory/` and `tool-results/` stay readable. Bash can still read them (in `default` mode it asks).
- The model can read any other non-denied file in `/app`, the md dir and the config dir (including agents, commands and settings). Its content goes to the Anthropic API and into session transcripts under `<dataDir>/config/projects`.
- Hiding of hidden/secret files from Grep and Glob rests partly on ripgrep and Claude Code behaviour plus best-effort deny rules.
- Bash reads of the login files cannot be fully prevented: the Bash check is a regex on the command text (credentials.json, .claude.json, config/backups) and globbing or obfuscation (`cat .cred*`, quoting tricks, backticks) bypasses it; closing that needs an allowlist or a sandbox.
- Claude Code's own login leaves a long-lived refresh token on disk (`config/.credentials.json`, mode 0600, written and refreshed by Claude Code); a Console login stores its API key in plain text in `config/.claude.json` and in `config/backups/`. yena does not read these files.
- The login probe relies on the undocumented shape of `auth status --json` and may write into the config dir; a revoked login still reads as signed in until Claude Code notices.
- The config dir is shared with `./yena claude code`, so a login made or refreshed in either place is the one both use. The email is printed on screen and never logged.
- Several yena processes changing the order or the pin at the same moment can lose one of the `auth.json` updates (each write is atomic, the read-modify-write is not).
- The credential channel is an in-process guard and audit point, not a hard boundary; the stored API keys sit encrypted in the account module, but this module holds them in memory (and the background runner receives them from yena over its 0600 socket).
- Env files: `claude ask` denies `**/.env*` outright. The chat's settings rules name only `**/.env` (they cannot express exceptions); the policy hook and the permission bridge refuse every other `.env*` name in every mode, except templates (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`, also `.env.<x>.example`; `ENV_TEMPLATE` in `src/policy.ts`), which the chat may read and write like any other dotfile (asked for at the top of the project). Secret names (`isSecretName`): `.env`, `.envrc`, `.env.<x>` / `.env-<x>` / `.env_<x>`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `.netrc`, `.npmrc`, `.pgpass`, SSH private keys `id_rsa`/`id_dsa`/`id_ecdsa`/`id_ed25519*`; not secrets: the env templates, `*.d.ts` (e.g. `.env.d.ts`) and public keys `id_*.pub`. The chat's settings rules name only `**/.env` and `**/id_rsa`; `claude ask` keeps the broad `**/.env*` and `**/id_rsa*`. Glob patterns and Grep `glob`s that are absolute or contain `..` are checked by the folder before their first wildcard (`globBase`), so `/app/src/**/*.ts` is allowed and `/etc/*`, `/**`, `*/../..` and `~/…` are refused.

Process lifetime (also for `chat`): a normal exit, timeout or cancel stops the `claude` child process. After SIGTERM or SIGKILL of the yena process the `claude` child can outlive it for a few seconds and exits when its stdin closes; it is not guaranteed, and a generation in progress may keep running until then (no signal handlers on purpose, so the host's signal behaviour is unchanged).

## Logging
The module logs through the host logger (`host.log`, scope `claude`) into `<YENA_DATA>/host/logs/yena.log` (`<YENA_HOME or cwd>/logs/yena.log` without `YENA_DATA`) (JSON lines; format, levels, rotation and redaction are described in the host `CLAUDE.md`). On a host without `host.log` it uses a local noop logger (`src/log.ts`) and nothing is written.

Records (level, message, fields):
- info `plugin loaded`.
- info `auth status` {kind, source, accounts}; info `auth order` {count}; info `auth use` {count}; info `auth auto` {cleared}; info `auth remove`; info `claude login started` {method, sso, email (boolean)}; info `claude login finished` {exitOk, loggedIn, method, subscriptionType}; info `claude logout` {ok, stillLoggedIn}; info `credential stored` {type: key}; info `credentials migrated` {moved, skipped, dropped}; warn `credential migration failed` {errClass, step}; info `auth state migrated`; warn `auth state not migrated` {errClass}; warn `retired credentials record unavailable` {errClass}; warn `credential store unavailable` {errClass}.
- warn `no credential` (ask and chat); info `credential resolved` {kind, source} (ask).
- info `ask started` {fresh, promptChars}; info `ask finished` {outcome, ms, model, numTurns, session8}; warn `ask failed` {outcome (`timeout`|`error`), ms, errClass, reason}; warn `ask timed out` {timeoutMs}; error `sdk load failed` {missingModule, err}.
- warn `result error` {subtype, authFailed}; warn `query threw` {errClass, aborted}.
- info `chat starting` {fresh, kind, source, resuming, model} (`model` is the chosen id or `default`); info `chat setting set` {key, value}; error `chat dependencies failed to load` {missingModule, err}; info `chat closed` {ms, session8, model}; info `session account kept`; warn `session subscription mismatch`; warn `session account not saved` {errClass}.
- info `account changing` (the warm process is dropped for the next account at a send); warn `account change failed` {errClass}; info `account changed` {reason: changed|pinned}; warn `account check failed` {errClass}; info `chat started with a message` {chars, byCaller, apiKeyOnly} (commands).
- info `sdk session spawned` {resuming}; info `turn started` {chars} (or {origin: 'claude-code'} for a turn Claude Code started); info `message steered` {chars}; info `turn continues` {queued}; info `first output` {ms, warm}; info `turn aborting` {outcome}; info `turn ended` {outcome, ms, reason?, calls?, cacheWrite?, cacheRead?, output?, agentCalls?, agentCacheWrite?, agentCacheRead?, agentOutput?}; warn `turn lock busy for a Claude Code turn`; warn `sdk stream threw` {errClass}; warn `sdk stream ended unexpectedly` {authFailed}; warn `authentication failed`; warn `interrupt grace expired; recycling` {graceMs}; warn `session recycled`.
- warn `state write failed` {code}; warn `process status write failed` {err} (once per chat), warn `process status remove failed` {err}; warn `exit hook aborting requests` {count}.
- info `session lock` {action: acquired|released|stale-removed, kind, where}; info `session stop` {where, via: socket|signal, ok}; info `runner spawned` {ms}, `runner attached`/`runner detached` {keep}, `runner exit` {reason, turns, ms}; info `chat remote` {action: spawned|attached|detached, running}; warn `chat remote` {action: lost|fallback}; warn `runner spawn failed`, `runner protocol error`, `runner frame failed`, `runner request failed`, `runner server error`, `runner open failed`, `control request failed`, `control server error`, `control stop failed`, `chat remote write failed`, `chat remote state update failed`, `queue flush failed`, `engine warning`, `initial mode rejected`; info `queue flushed` {count}, `chat closed` {ms}: metadata only.
- info `route` {outcome: rated|kept|pinned|off, tier?, rated?, newTask?, held?, reason?, ms?, inTokens?, outTokens?}; info `tier set` {tier}; info `agent routed` {tier, source}; debug `classifier failed` {errClass}, `agent tier invalid`, `agent definition skipped` {reason}, `agent definitions` {count, skipped}; warn `agent definitions failed` {errClass}.
- warn `shell tmp unavailable` {error class}; debug `shell view` {shown, calls, ms, outputBytes, bound (`file`|`task`), fallback (`busy`|`focus`|`ambiguous`|`nofile`|`tmp`)}: metadata only.

`reason`/`err` values are scrubbed with the credential redactor and clipped to 300 characters.

Never logged: the prompt (only its length), assistant text, tool arguments and results, file contents, the environment, the credential or any part of it.

`registerLogValues` (`src/credentials.ts`) adds an exact-value redactor for every stored API key and for `ANTHROPIC_API_KEY`, to the logger (once per value, keyed by a SHA-256 digest) whenever the credentials are loaded, before `credential resolved` and every later record, in addition to the host's built-in patterns.

## Claude Code wrapper
`./yena claude code` (from the host repo) runs `bin/claude`, unchanged by the `ask` work; it reads no credential files (see Credentials). Its `GUARD` and `HINT` strings are kept in sync with `src/config.ts` by a test. `bin/install` refreshes Claude Code in `.runtime/`, and runs `npm install --prefix <module>` when `npm ls --omit=dev --depth=0` finds a module dependency missing or at another version (the Agent SDK pinned to 0.3.302, matching the runtime,). A failed install prints `Failed to install module dependencies`.

## Development
From `modules/claude`: `npm install && npm run typecheck && npm test` (`npm test` runs the `.ts` and `.tsx` tests under `tests/`; `typecheck` also checks them via `tests/tsconfig.json`). `tsc` and `tsx` still come from the host's `node_modules` and types are imported from the host's `src/api.ts`, so this only works inside the host tree. The SDK and its peers are installed in the module's own `node_modules`. Tests fake the SDK. `ink` and `react` come from the host (`/app/node_modules`) and must not be added to this module's dependencies. Every `.tsx` file must start with `import React from 'react'`: yena runs tsx from `/app`, where the module's JSX settings do not apply, and `npm test` (cwd = the module) would not notice. `tests/ui/runtime.test.ts` renders the UI components in a subprocess started from the host root to catch this (on failure it reports a missing frame text, not the `ReferenceError`). From the host root, `npm run typecheck:modules` and `npm run test:modules` run these for every module.

Manual live check: use a throwaway session and a cheap model, with the credential only in the environment and never printed:

## Permissions that persist
"Always" for a Bash command, an MCP tool (`mcp:<tool>`) or a console command (`cmd:<command> <subcommand path>`) is saved in `state.json` (`allowedCommands`, at most 200) and applies to later chats; the `Permissions` settings tab (shown when there are rules) lists them, and choosing Remove drops one (also from the open chat). MCP tool calls always ask unless allowed this way (auto mode: the classifier decides first); their prompt shows the tool and its JSON arguments.
